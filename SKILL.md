# Next.js JS Standards

## Standing Principle
All UI design and APIs in this project will be refactored and professional, properly structured and dynamic — never treat a screen or endpoint as a one-off. Every new section reuses the shared components, typography scale, theme colors, and folder structure below, and every API is built for real data (params, validation, error states), not hardcoded stubs.

## Database: PostgreSQL Migration Is Underway (Module by Module)
- This project simulates most of its backend with in-memory arrays in `lib/*.js` (`lib/notices.js`, `lib/homework.js`, `lib/houses.js`, `lib/academicSessions.js`, etc.), stashed on `globalThis` to survive Next.js dev Fast Refresh. **This is being migrated to a real Postgres database module by module** — not a future-phase placeholder anymore, an in-progress one. Auth (Super Admin/School Admin), Students, Teachers, Classes & Sections, and Attendance are migrated so far (see "Backend Migration: Auth API on Postgres + Prisma", "Teachers Module Migrated to Postgres", "Classes & Sections Module Migrated to Postgres", and "Attendance Module Migrated to Postgres" below). Only migrate a module when the user explicitly asks; the rest of `lib/*.js` stays in-memory until its turn.
- **Table naming convention once a module migrates**: the Prisma model identifier stays singular (`model Student`, `model Teacher` — so `prisma.student.*`/`prisma.teacher.*` call sites read naturally and don't need to change), but the physical table is mapped to its plural form via `@@map("Students")`/`@@map("Teachers")`. Follow this same `@@map` convention for any future migrated module rather than leaving the table name matching the singular model name.
- Keep this in mind when writing or extending an **still-in-memory** `lib/*.js` module: favor shapes and access patterns that translate cleanly to relational tables and SQL queries later (flat-ish records with clear foreign-key-style id references like `classId`/`classTeacherId`, functions named/scoped like a data-access layer — `getAllX`, `getXById`, `addX`, `updateX` — rather than ad-hoc array gymnastics scattered through components). Don't invent data shapes that would be awkward to migrate (e.g. deeply nested objects that should really be separate tables/relations) if a flatter, join-friendly shape is just as easy to write now.
- **A migrated module keeps its old exported function names/signatures wherever possible** (see `lib/admins.js`'s Prisma rewrite) — its callers (API routes, page components) shouldn't need to change just because the internals swapped from an array to a query. Cross-module joins between a migrated table and a still-in-memory store (e.g. a DB `SchoolAdmin.schoolId` joined against `lib/schools.js`'s in-memory school list) happen at the application layer, not via a real foreign key, until both sides are migrated.

## Optimistic UI Updates — No Refetch on Mutation (Standing Rule, All APIs)

**Every mutating action (create/update/delete/status-toggle) must update local React state directly from the response it already has, instead of calling `router.refresh()` or re-running a GET to reflect its own result.** `router.refresh()` re-executes the whole server component tree's data fetching just to show a change the client-side code already knows the outcome of — that's a wasted API/DB round trip on every single action, and it's the default trap to avoid when wiring up a new mutation in this app.

**Pattern**: the page-level "explorer"/list component takes the server-rendered array as its *initial* value only, holds its own copy in `useState`, and every mutation updates that state array directly (`setList((prev) => prev.map(...))` for edits/status toggles, `setList((prev) => prev.filter(...))` for deletes) — never `router.push`/`router.refresh` just to reflect the mutation. A deeply-nested action component (a row's dropdown menu, a card's delete button) doesn't own the list itself — it calls back up (`onUpdated`/`onDeleted` props) to whichever ancestor holds the state, the same way `StudentActionsMenu` → `StudentsTable` → `StudentsExplorer` is wired, or `SchoolsTable` → `SchoolsDirectory`.

Reference implementations to copy this pattern from:
- **`SchoolsDirectory.jsx`** / **`SchoolDetailsHeader.jsx`** — status toggle updates `schoolsList`/`status` state directly instead of `router.refresh()`.
- **`StudentsExplorer.jsx`** / **`StudentActionsMenu.jsx`** — delete calls `onDeleted(id)` up to `StudentsExplorer`, which filters its own `studentsList` state, instead of `router.refresh()` re-running `getAllStudents()`.

**Known, accepted tradeoff**: a *sibling* stat/summary card that was computed server-side once (e.g. the Students page's `StatsCards`, built from `getStudentStats()` in the server component) will go stale after an optimistic update on the list below it, until the next real navigation to that page. This is intentional — the alternative (refetching to keep that one card perfectly live) is exactly the extra API call this rule exists to avoid. If a stat absolutely must stay live-accurate every second, derive it client-side from the same local list state instead of trusting the server-rendered prop.

**Also converted: Super Admin Admins directory** (`AdminsDirectory.jsx` list page, `SchoolAdminCard.jsx` on a school's detail page) — status toggle, permissions edit, and create-admin all now patch local state from the mutation's own response instead of `router.refresh()`. Note this one didn't even need a second GET: every admin API route (`PATCH /api/admins/[id]/status`, `PATCH /api/admins/[id]/permissions`, `POST /api/schools/[id]/admin`) already returns the full updated/created record in its response body — `updateAdminStatus`/`updateAdminPermissions`/`createSchoolAdmin` (`lib/api.js`) just needed their return value actually *used* instead of discarded. `ResetPasswordDialog`'s `onSuccess` had no data to reflect anywhere (no screen shows `lastPasswordResetAt`), so its `router.refresh()` was dropped with no replacement at all. **Before reaching for local state, check whether the mutation's own API response already has what you need** — often it does, and no extra plumbing (callback props, merge logic) is required beyond using it.

**Still using the old `router.refresh()`-after-mutation pattern, not yet converted** (fix opportunistically when touching these, not required as a one-off sweep): Notices, Homework, Classes & Sections, Academic Sessions, Teachers. Same fix applies: lift the list into local state, update it directly in the mutation's success handler (check the API response for the updated record first), drop the `router.refresh()`.

## Pixel-Perfect Fidelity From Designs
When the user provides an image or screenshot of a screen to build, match it with 100% accuracy — pixel-perfect. That means:
- Exact layout and structure (stacked vs. inline elements, alignment, centering)
- Exact spacing (margins, padding, gaps) and sizing (font sizes, icon sizes, corner radii, card width)
- Exact colors, including gradient direction and stops — sample them from the image rather than guessing
- Exact copy/wording shown in the design, exact icon choices
- Do not "interpret" or simplify a provided design — reproduce it faithfully, then apply this project's component/validation/structure standards underneath it.

## Form Validation
- **Stack**: React Hook Form + Zod for every form — no manual `useState`-per-field or hand-rolled validation. Install: `npm install react-hook-form zod @hookform/resolvers`
- Each form has its own Zod schema in `lib/schemas.js` (or a dedicated `lib/schemas/<form>.js` for larger forms), with custom rules (regex, min/max, refine) per field — not just `.min(1)` "required" checks.
  ```javascript
  // lib/schemas.js
  import { z } from 'zod';

  export const loginSchema = z.object({
    email: z.string().min(1, 'Email is required.').email('Enter a valid email address.'),
    password: z.string().min(6, 'Password must be at least 6 characters.'),
  });
  ```
- Wire the schema into the form with `zodResolver`:
  ```javascript
  'use client';
  import { useForm } from 'react-hook-form';
  import { zodResolver } from '@hookform/resolvers/zod';
  import { loginSchema } from '@/lib/schemas';

  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm({ resolver: zodResolver(loginSchema) });
  ```
- Validation errors are field-level, not a single form-wide banner: each `Input` renders its own error message directly below itself, tied to that specific field via RHF's `errors.<field>?.message`.
- The `Input` component accepts an `error` prop and forwards `register(name)` — when `error` is set, it shows a red border and a `text-xs text-red-500 mt-1` message under the field; it returns to normal once the field is corrected (RHF re-validates on change by default once a field has errored).
- Reserve a top-of-form error only for server/API-level failures (e.g. "Invalid credentials", network error) — never for per-field validation issues. Surface these via a small piece of local state set from the `handleSubmit` success/catch, not from RHF's `errors`.
- Use `isSubmitting` from `formState` to disable/label the submit button during the request, instead of a separate `isLoading` state.

## Typography
- **Font**: Geist Sans (via `next/font/google`), applied globally as `--font-geist-sans`
- Set up once in `app/layout.jsx`:
  ```javascript
  import { Geist, Geist_Mono } from "next/font/google";

  const geistSans = Geist({
    variable: "--font-geist-sans",
    subsets: ["latin"],
  });

  const geistMono = Geist_Mono({
    variable: "--font-geist-mono",
    subsets: ["latin"],
  });
  ```
- Wired into Tailwind's `font-sans` via `app/globals.css`:
  ```css
  @theme inline {
    --font-sans: var(--font-geist-sans);
    --font-mono: var(--font-geist-mono);
  }
  ```
- Do not introduce other sans-serif font families; use `font-sans` (default) everywhere text needs the brand typeface.

## Typography Scale
Use these consistently across every screen — don't invent one-off sizes.

| Role | Classes | Example use |
|---|---|---|
| Brand / Logo text | `text-2xl font-bold text-gray-900` | "EduManage" wordmark |
| H1 — Page title | `text-2xl font-bold text-gray-900` | Top-level page heading |
| H2 — Section title | `text-lg font-semibold text-indigo-700` | "Welcome back", card/section titles |
| H3 — Subsection title | `text-base font-semibold text-indigo-700` | Grouped content headers within a section (e.g. `FormSection` titles like "Basic Information") |
| Body text | `text-sm text-gray-600` | Standard paragraph/content text |
| Description / helper text | `text-sm text-gray-500` | Text under a heading, form helper text |
| Label | `text-sm font-medium text-gray-700` | Form field labels |
| Caption / small print | `text-xs text-gray-400` | Footnotes, timestamps, fine print |

- Never hardcode a font size outside this scale; if a new case doesn't fit, extend the table rather than picking an arbitrary class.
- Headings always use `font-bold` or `font-semibold`; body/description text never uses `font-bold`.
- H1/Brand wordmark stay `text-gray-900` (solid neutral, per Theme Colors); **H2 and H3 section/subsection titles use the theme blue `text-indigo-700`** — every `FormSection`/card/panel title ("Basic Information", "System Access", "Documents", modal titles, success-screen headings, etc.) picks up this color, not `text-gray-900`.

## Theme Colors
- **Primary brand gradient**: violet → indigo → blue, used for primary actions, active states, and brand accents
  - Buttons / CTAs: `bg-gradient-to-r from-violet-700 via-indigo-600 to-blue-600`
  - Active toggle/tab state: `bg-gradient-to-r from-violet-700 via-indigo-600 to-blue-600` (same as CTA gradient)
  - Logo / icon badges: solid `bg-violet-700` (flat color, not a gradient)
  - Brand wordmark text (e.g. "EduManage"): solid `text-gray-900 font-extrabold` (not the gradient — gradient is for surfaces/CTAs only)
- Page background: soft lavender-to-white gradient, e.g. `bg-gradient-to-br from-indigo-50 via-white to-blue-50`
- Use the CTA gradient consistently for anything that represents the primary/confirming action (Sign In, Send Reset Link, Save, Continue, active tab) across all future sections — do not introduce alternate accent colors for these roles.
- Neutral surfaces stay white/gray (`bg-white`, `bg-gray-50`, `border-gray-200`, `text-gray-500/700/900`); the gradient is reserved for emphasis, not backgrounds.

## Layout & Scrolling
- The `html`/`body` root is fixed to the viewport (`h-full overflow-hidden` on `body` in `app/layout.jsx`) — the page shell itself never scrolls.
- Full-screen/centered screens (auth, splash, empty states) fit within the viewport with content centered via `flex items-center justify-center` — no page-level scrollbar.
- Any screen whose content can exceed the viewport (dashboards, tables, forms with many fields) must scope scrolling to its own inner container (`overflow-y-auto` on that container), not the whole page.
- **Scrollbars are thin everywhere**: defined once, globally, in `app/globals.css` — `scrollbar-width: thin` (Firefox) plus a `::-webkit-scrollbar` override pinning width/height to `2px` with a transparent track and a soft rounded thumb. Never add per-component scrollbar overrides; the global rule already covers every scrollable container (page, dropdown panels, tables, drawers).

## Field Shape
- Every field-like control — `Input`, `Dropdown` trigger, `DatePicker` trigger, and standalone search bars (topbar, toolbars) — uses the same fully-rounded pill shape: `rounded-full` with a `border-gray-200` (default) / `border-gray-900` (open) / `border-red-400` (error) border. This is the one shape for anything the user types into or picks a value from; don't mix in `rounded-lg`/`rounded-xl` inputs alongside pill dropdowns on the same form.
- Buttons and cards keep their own radii (`rounded-lg`/`rounded-xl`/`rounded-2xl` per their existing rules) — the pill shape is specific to form fields, not every rounded element on the page.

## Motion & Transitions
- Any collapsible/expandable content (sidebar submenus, accordions, expandable cards) must animate open/close smoothly — never toggle with a plain `{isOpen && <div>...}` conditional render, which snaps instantly with no transition.
- Pattern: wrap the collapsible content in a grid container and animate `grid-template-rows` between `'0fr'` and `'1fr'` (via inline `style`, since Tailwind has no arbitrary-value utility for animatable `fr` units), with an `overflow-hidden` child holding the actual content. This animates a true "auto height" open/close, which a plain `max-height` transition can't do reliably for variable-height content.
  ```jsx
  const [isExpanded, setIsExpanded] = useState(false);
  // ...
  <div
    className="grid transition-[grid-template-rows] duration-300 ease-in-out"
    style={{ gridTemplateRows: isExpanded ? '1fr' : '0fr' }}
  >
    <div className="overflow-hidden">
      {/* collapsible content, e.g. submenu links */}
    </div>
  </div>
  ```
- Keep the chevron/caret icon's rotation (`rotate-180`) transition (`transition-transform`) in sync with the same duration so the icon and panel animate together.
- Sidebar's `NavGroup` (submenu for Students, etc.) uses this pattern — reuse it for any future collapsible nav group or accordion rather than reintroducing a plain conditional render.

## DropdownMenu Rendering (Portal, Not Inline)
- `components/DropdownMenu.jsx` (the row/profile "⋮" actions popup) renders its panel through a **React portal to `document.body`**, positioned with `position: fixed` from the trigger button's `getBoundingClientRect()` — it does not render inline inside the table/card DOM tree.
- Why: any ancestor with `overflow-x-auto` (e.g. the table wrapper) computes `overflow-y` as clipped too, per the CSS spec's overflow-pairing rule — a plain `absolute` popup nested inside that ancestor gets its bottom cut off for rows near the end of the table/page, exactly the "menu opens but I can't see all the items" bug. A portal escapes that ancestor entirely, so this can't happen regardless of where the trigger sits.
- It also **flips upward** automatically when there isn't enough viewport space below the trigger (computed against `window.innerHeight`). On scroll/resize it **recomputes and re-anchors its position** rather than closing — closing on every scroll was tried and felt broken (the Topbar avatar menu would vanish the instant the page scrolled), and since position is recalculated from `getBoundingClientRect()` on each scroll/resize event there's no need to close just to stay accurate.
- Menu sizing: `MENU_WIDTH = 208`, `ITEM_HEIGHT = 40`, items rendered at `text-sm` with `px-3.5 py-2.5` — a prior smaller version (`192`/`30`/`text-[10px]`) read as cramped/too-small and was bumped up. Keep new items within this sizing rather than shrinking it back down.
- Any future popover/menu that's triggered from inside a scrollable table or card should follow this same portal + viewport-aware-flip pattern — don't reach for a plain `absolute` `<div>` nested in the trigger's parent.

## Account Menu (Topbar Avatar, Not Sidebar Footer)
- **Profile and Logout live in the Topbar's avatar dropdown**, not the sidebar footer. `components/dashboard/Topbar.jsx` wraps the avatar circle + a `FiChevronDown` in a `DropdownMenu` trigger; its two items are "Profile" (`router.push('/dashboard/profile')`) and "Logout" (`danger`, opens a `ConfirmDialog` — it does not log out immediately on click).
- `components/dashboard/Sidebar.jsx`'s bottom section keeps only the **Support** button — Profile/Logout were removed from there. Don't re-add per-user account actions to the sidebar footer; the Topbar avatar is the one place for them.
- **Logout always confirms first**: clicking "Logout" opens a `ConfirmDialog` ("Log out?" / "You'll need to sign in again to access EduManage." / confirm label "Log Out"); only confirming actually calls `router.push('/login')`. This is the same confirm-before-destructive-action pattern used for Deactivate elsewhere — logging out isn't literally destructive, but it's a one-click way to lose your place in the app, so it gets the same guard.

## Modal, Confirmation & Toggle Components
- **Modal** (`components/Modal.jsx`): the one pattern for any dialog/drawer-style overlay (Assign Class, future create/edit-in-place flows) — a centered `rounded-2xl` white card over a `bg-black/40` backdrop, closes on backdrop click or `Escape`, title + optional description + close (`FiX`) button in the header, arbitrary `children` for the body/form. Don't hand-roll a one-off overlay `<div>` for a new modal — wrap it in `Modal`.
- **ConfirmDialog** (`components/ConfirmDialog.jsx`): built on `Modal`, the one pattern for confirming a destructive action (deactivate, remove assignment, delete, logout) — title, description, Cancel (gray) + a solid red confirm button, with an `isLoading` state that disables the confirm button and swaps its label to "Please wait...". Use this instead of `window.confirm()` or a bespoke inline confirmation for anything destructive. Both buttons are plain `w-full sm:w-auto` buttons (stacked full-width on mobile via `flex-col-reverse`, side-by-side auto-width on `sm+`) — don't give Cancel the shared `Button` component's `fullWidth` prop on its own, since that stretches it to fill the row on desktop while the confirm button stays auto-width, producing a lopsided pair.
- **This same lopsided-pair bug applies to every modal footer built from the shared `Button` component** (`ClassFormModal`, `SectionFormModal`, `AssignSectionTeacherModal`, `AssignClassModal`, and any future Add/Edit modal with a `flex-col sm:flex-row justify-end` footer): `Button`'s `fullWidth` prop renders unconditional `w-full`, with no responsive variant. Giving Cancel `fullWidth` directly makes it fill the whole row on desktop while the submit `Button` (no `fullWidth`) stays content-width, producing mismatched button sizes/heights. The fix used throughout this codebase (see `TeacherForm.jsx`/`StudentForm.jsx`'s Cancel `Link`) is to **wrap Cancel's `Button` in a `<div className="w-full sm:w-auto">`** and keep `fullWidth` on the inner `Button` (so it fills that wrapper, not the whole flex row) while the submit `Button` gets `fullWidth={false}`. Never give Cancel bare `fullWidth` inside a `sm:flex-row` footer without this wrapper.
- **Toggle** (`components/Toggle.jsx`): the one pattern for a boolean on/off control (e.g. "Give this teacher login access") — a pill switch using the brand gradient when checked, gray when unchecked, with an optional `label`/`description` pair to its left. Not a native form element; it's driven by plain `checked`/`onChange` (local `useState`), not RHF `register`/`Controller`, since it represents a UI toggle rather than a field with its own validation.
- Destructive row/menu actions (Deactivate teacher, Remove assignment, etc.) follow: click → open `ConfirmDialog` → on confirm, call the API, close the dialog, show a `Toast`, and `router.refresh()` the current route to reflect the change (the in-memory `lib/*.js` store already mutated server-side; `refresh()` just re-fetches the Server Component data).

## Mandatory Identity Documents (Aadhaar)
- Every person record (Student, Teacher, and any future person-type module) captures **Aadhaar Card Number** (a required text `Input` in that module's Personal/Basic Information section) and a **mandatory Aadhaar Card upload** (in that module's Documents section) — both required at creation, validated via Zod in `lib/schemas.js`:
  ```javascript
  const AADHAAR_REGEX = /^\d{4}\s?\d{4}\s?\d{4}$/;
  const aadhaarNumberField = z.string().min(1, 'Aadhaar number is required.').regex(AADHAAR_REGEX, 'Enter a valid 12-digit Aadhaar number.');
  const aadhaarDocumentField = z.custom(
    (val) => (typeof File !== 'undefined' && val instanceof File) || (typeof val === 'string' && val.length > 0),
    { message: 'Aadhaar card upload is required.' }
  );
  ```
- **`FileDropzone` is controllable**, the same way `Dropdown`/`DatePicker` are: pass `value`/`onFileSelect` (wired via `Controller`, plus `required` to render the red asterisk) to make it a validated RHF field instead of the default uncontrolled/no-op usage other optional documents still use:
  ```javascript
  <Controller
    name="aadhaarDocument"
    control={control}
    render={({ field }) => (
      <FileDropzone label="Aadhaar Card" accept="application/pdf,image/*" required value={field.value} onFileSelect={field.onChange} error={errors.aadhaarDocument?.message} />
    )}
  />
  ```
- Since there's no real file storage backend, a selected `File` is never sent to the API as-is (it can't survive `JSON.stringify`) — each form's local `onSubmit` converts it to `file.name` before calling the parent handler: `aadhaarDocument: data.aadhaarDocument instanceof File ? data.aadhaarDocument.name : data.aadhaarDocument`. The `lib/<module>.js` record stores this as `aadhaarDocumentName`. On Edit, `defaultValues.aadhaarDocument` is seeded with the existing `aadhaarDocumentName` string, so `FileDropzone` renders it as an already-uploaded file (green "Uploaded" state, no re-upload forced) unless the user replaces it.
- The Documents section/tab lists a document as an object `{ label, required, getFileName(record) }`, not a bare string, whenever its upload/status is real (backed by a stored field) rather than a static Phase-1 placeholder — `getFileName` returns the record's `aadhaarDocumentName` (or `undefined` for a placeholder-only doc), and the tile's icon/status/asterisk are derived from that, not hardcoded per document.
- **Student's guardian also carries Aadhaar**: `guardianSchema` (primary guardian, required) includes `aadhaarNumber`/`aadhaarDocument` with the same required validators as the student's own; `secondaryGuardianSchema` (optional guardian) includes the same two fields but optional/unvalidated. `GuardianFields.jsx` renders only the Aadhaar Number `Input` inline (grouped with the guardian's other identity fields); the guardian's Aadhaar Card **upload** is not rendered there — it lives in the Student form's "Documents and Photos" section instead.
- **Father Aadhaar / Mother Aadhaar are two separate upload fields**, not one combined "Parent Aadhaar Card": "Father Aadhaar" is a `Controller` on `guardian.aadhaarDocument` (required — reuses the primary guardian's already-required schema field) and "Mother Aadhaar" is a `Controller` on `secondaryGuardian.aadhaarDocument` (optional — reuses the secondary guardian's already-optional schema field, with no `required` prop). Because the Mother Aadhaar upload can be filled in independently of the rest of the (optional) secondary-guardian block, `lib/students.js`'s `buildStudentFields()` keeps `secondaryGuardian` in the saved record if **either** `fullName` or `aadhaarDocument` is present — checking `fullName` alone would silently drop an uploaded Mother Aadhaar file when the rest of that guardian's details were left blank. The Student Documents tab mirrors this as two required-vs-optional tiles: "Father Aadhaar" (`student.guardian.aadhaarDocumentName`, required) and "Mother Aadhaar" (`student.secondaryGuardian?.aadhaarDocumentName`, optional).
- **All person/photo uploads for a module are consolidated into one "Documents and Photos" section** at the bottom of the form — never a photo `FileDropzone` in the Basic/Personal Information section, for any module. For Students this section holds, in order: Aadhaar Card* (student), Father Aadhaar* (guardian), Mother Aadhaar (secondary guardian, optional), Student Photo, Father Photo, Mother Photo, Birth Certificate, School Leaving Certificate (SLC), Other Document. For Teachers: Aadhaar Card*, Profile Photo, 10th Certificate, 12th Certificate, Graduation Certificate. Everything after the required Aadhaar card(s) is optional, uncontrolled (`onFileSelect={() => {}}`) placeholders like any other Phase-1 document. Mirror this consolidated placement — including moving any profile-photo field there — for any future module rather than leaving a photo upload in the identity-info section.

## Nationality Dropdown (Country List)
- Nationality is a searchable `Dropdown`, never a free-text `Input` — sourced from `country-state-city`'s `Country` module (the same package already used for Indian states/cities), via `getNationalityOptions()` in `lib/location.js`. It returns `{ value: country.name, label: country.name }` for every country, with **India pinned first** and the rest alphabetically sorted after it — don't re-sort India into alphabetical order. This mirrors the existing State/City dependent-dropdown pattern: reuse a real data library instead of hardcoding a country list, and mark it `searchable` per the 100+-option rule.

## Student HR/Contact Fields (WhatsApp, Portal Access, Previous School, Emergency Contacts, Fees)
- **Basic Information** additionally captures `whatsappNumber` (plain `Input`, for update notifications) alongside the existing Aadhaar Number field.
- **"Previous School Details"** is its own `FormSection` (optional): `previousSchoolName` (Input), `previousSchoolBoard` (Dropdown, `SCHOOL_BOARDS` from `lib/students.js`: CBSE/ICSE/State Board/IB/IGCSE/Other), `lastClassPercentage` (Input).
- **"Student Portal Access"** is a one-field `FormSection`: `portalEmail` — the email the student/parents use to sign in to the student portal/app. Distinct from the guardian's own `email` field; email-validated but optional.
- **"Emergency Contacts"** is its own `FormSection` (not shared with Parent/Guardian): a **primary** contact (`primaryEmergencyName`/`primaryEmergencyRelationship`/`primaryEmergencyPhone`) and a **secondary** contact (same three fields, `secondaryEmergency*`), both using `EMERGENCY_CONTACT_RELATIONSHIPS` from `lib/students.js` (Grandparent/Uncle-Aunt/Family Friend/Neighbor/Sibling/Other — distinct from `GUARDIAN_RELATIONSHIPS`, since an emergency contact isn't necessarily a parent), plus a standalone `trustedRelativePhone`. All optional.
- **"Fee Details"** is its own `FormSection`: `admissionFeePaidDate` (DatePicker), `admissionFeeAmount` (Input), `feeStructureType` (Dropdown, `FEE_STRUCTURE_TYPES`: Monthly/Annual), `feeStructureAmount` (Input), `feePaymentStatus` (Dropdown, `FEE_PAYMENT_STATUSES`: Paid/Pending/Partial/Overdue), `outstandingDues` (Input). All optional. The Student Profile's **Fees tab is functional** (not "Soon") and renders this via one `InfoCard`, with a small `formatCurrency()` helper (`₹` prefix) in `ProfileTabs.jsx`.
- **Storage shape**: `lib/students.js`'s `buildStudentFields()` nests these as `previousSchool: { name, board, lastClassPercentage }`, `emergencyContacts: { primary: {...}, secondary: {...}, trustedRelativePhone }`, and `feeDetails: { admissionFeePaidDate, admissionFeeAmount, structureType, structureAmount, paymentStatus, outstandingDues }`, plus flat `whatsappNumber`/`portalEmail` — same nesting convention as `address`/guardian records. `EditStudentForm.jsx` flattens these back out into the form's flat field names when building `defaultValues`.
- **Attendance stays "Coming Soon"**: the Attendance tab (daily records, absences with reasons, leave applications/approvals, late-coming records) is explicitly out of scope for this phase — keep its tab `comingSoon: true` and don't build fields for it until asked. This is different from Fees, which the user gave concrete fields for and which is therefore live now — don't lump a "coming soon" instruction onto a section that was actually specified.

## Teacher HR Fields (Marital Status, PAN, Education, Bank, Emergency Contact)
- **Personal Information** additionally captures `maritalStatus` (Dropdown, `MARITAL_STATUSES` from `lib/teachers.js`: Single/Married/Divorced/Widowed), `nationality` (plain `Input`), and `panNumber` (plain `Input`, optional but format-validated when present via `panNumberField` in `lib/schemas.js` — regex `^[A-Z]{5}[0-9]{4}[A-Z]$`, same "optional-but-validated-if-filled" pattern as other non-mandatory identity fields).
- **"Education Details"** is its own `FormSection` (text fields only, no uploads — the matching certificates live in "Documents and Photos" per the consolidation rule above): `tenthPercentage`, `twelfthPercentage`, `graduationDegree`, `graduationUniversity`. All optional.
- **"Documents & Verification"** is a custom section (not a plain `FormSection` — it mixes a text-field grid with a `Toggle` and a conditional upload, the same freeform-`<div>` pattern already used for "System Access"): a bank-details grid (`bankAccountHolderName`, `bankName`, `bankAccountNumber`, `bankIFSC`, all optional plain `Input`s) plus a **Fresher `Toggle`** (local `useState`, default `true`, passed into `onSubmitProp` alongside `loginAccessEnabled` — not part of the Zod schema, same convention as other Toggle-driven flags). When the toggle is off (experienced), a "Work Experience Certificate" `FileDropzone` appears below it — uncontrolled/optional, same Phase-1 placeholder convention as other non-mandatory documents. This is the one place a `FileDropzone` sits outside "Documents and Photos": the user's own naming ("Documents & Verification") groups it with the bank-detail fields it verifies, not with the generic uploads section.
- **"Emergency Contact"** is a `FormSection` with `emergencyContactName`, `emergencyContactPhone` (both plain `Input`, optional), and `emergencyContactRelationship` (Dropdown, `EMERGENCY_RELATIONSHIPS` from `lib/teachers.js`: Spouse/Parent/Sibling/Child/Friend/Other).
- **Storage shape**: `lib/teachers.js`'s `buildTeacherFields()` nests these under `education: { tenthPercentage, twelfthPercentage, graduationDegree, graduationUniversity }`, `bankDetails: { accountHolderName, bankName, accountNumber, ifsc }`, and `emergencyContact: { name, phone, relationship }` on the teacher record, plus flat `maritalStatus`, `nationality`, `panNumber`, and `isFresher` fields — mirroring the `address`/`loginAccess` nesting convention already used for the rest of the record. `EditTeacherForm.jsx` flattens these nested objects back out into the form's flat field names when building `defaultValues`, the same unwrap-on-edit pattern used for `address`/`loginAccess`.
- All of these new fields (except PAN's format check) are optional — no `required` asterisks, no blocking validation. Follow this precedent for future HR-style fields: default to optional unless the user explicitly says a field is mandatory.

## Compact Upload Boxes
- `FileDropzone` renders as a small fixed-size square tile (`w-28 h-28`), not a wide full-column dashed banner. This applies everywhere the component is used (Student Photo, Aadhaar uploads, guardian Aadhaar, Profile Photo, qualification/graduation docs, etc.) — never wrap a `FileDropzone` in a `sm:col-span-2 lg:col-span-3` full-row span; let it sit as a normal single grid cell like any other field.
- The field's title is **written outside/below the box**, never inside it — `text-xs`, center-aligned under the box, clamped to 2 lines (`line-clamp-2 break-words`) so a long label (e.g. "Previous School Certificate") wraps instead of overflowing. The `required` asterisk lives in that same title line. **The title never changes to the filename** — it stays the field's fixed label (e.g. "Aadhaar Card") in both the empty and filled states, so the user always knows what each box represents regardless of what they uploaded.
- **No "uploaded/verified" indicator (tick, badge, or otherwise) is shown on the box or next to the title** — the filled-vs-empty box state (image/icon visible vs. dashed upload prompt) is the only signal needed. Don't reintroduce a checkmark, "Uploaded" text, or similar badge here; this was tried and explicitly rejected.
- **An uploaded image fills the entire box** — `w-full h-full object-cover` inside the fixed `w-28 h-28` frame, no inner padding shrinking it down to a small icon. A non-image file (PDF, etc.) instead centers a large `FiFile` icon filling the same frame. The remove (`FiX`) button overlays the top-right corner of the box.
- A section made up mostly/entirely of `FileDropzone`s (e.g. "Documents and Photos") should pass `contentClassName="flex flex-wrap gap-4"` to `FormSection` instead of the default 3-column grid — the grid stretches each box's cell to a third of the row width, leaving large gaps around the small fixed-size box; `flex flex-wrap` packs the boxes tightly and wraps naturally at the container edge. Keep the default grid for sections mixing `FileDropzone` with regular full-width fields (Input/Dropdown/DatePicker).

## Rules
- **Language**: JavaScript only, no TypeScript
- **Components**: Everything is a reusable component (buttons, inputs, forms)
- **Structure**: 
  - `/components/` - UI components (Client Components)
  - `/components/server/` - Server Components
  - `/components/icons/` - Custom icon components only for icons that don't exist in `react-icons` (one SVG per file)
  - `/pages/` - Route pages with Server-Side Rendering (SSR)
  - `/lib/` - Utilities and helpers
  - `/store/` - Redux state
  - `/api/` - API routes (server-side)
  - `/public/images/` - Static image assets (photos, illustrations, logos)
- **File naming**: PascalCase for components, camelCase for functions
- **File extensions**: Any file containing JSX must use `.jsx` (components, pages, layouts) — not `.js`. Plain logic files with no JSX (`lib/`, `store/`, API routes) stay `.js`
- **Interactivity**: Every clickable element (`<button>`, toggle, tab, link acting as a button) must have `cursor-pointer` in its className so click/hover always shows a pointer cursor
- **Exports**: Default exports for components
- **State**: useState for client state, Redux for global client state
- **SSR**: Use Server Components by default, Client Components only when needed ('use client')
- **Functions**: Separate file for each function group (api calls, formatters, validators, etc.)
- **Icons**: Use `react-icons` for all icons — install with `npm install react-icons`. Prefer the `react-icons/fi` (Feather) set for line icons (mail, lock, eye, arrow, send, etc.) for a consistent stroke style; use brand-specific sets (`react-icons/fc`, `react-icons/fa`) for third-party logos (Google, Microsoft, etc.). Import only the specific icons used, e.g. `import { FiMail } from 'react-icons/fi'`. Only hand-roll a custom SVG component in `/components/icons/` when no suitable icon exists in `react-icons`.
- **Dates**: Never use the browser's native `<input type="date">` (or any default OS/browser date widget) — its styling can't be themed and looks inconsistent across browsers. Use the shared `components/DatePicker.jsx` everywhere a date is picked (date of birth, admission date, filters, etc.):
  - A compact custom dropdown calendar: a gradient header showing the selected/pending date, month/year navigation with a year-list quick-jump, a day grid (today outlined, selected day filled with the brand gradient), and `Cancel`/`OK` actions that commit the pending selection. Keep the panel's width matched to its trigger field and its type sizes compact — it's a small utility popover, not a hero element.
  - Value format is a plain `YYYY-MM-DD` string, same as a native date input, so it drops into existing schemas/APIs unchanged.
  - It is not a native form element, so wire it into React Hook Form via `Controller`, not `register`:
    ```javascript
    <Controller
      name="dob"
      control={control}
      render={({ field }) => (
        <DatePicker value={field.value} onChange={field.onChange} error={errors.dob?.message} />
      )}
    />
    ```
- **Dropdowns/Selects**: Never use a native `<select>` — its options list can't be styled and looks inconsistent across browsers/OSes. Use the shared `components/Dropdown.jsx` everywhere a choice is picked from a list (gender, class, section, status, filters, etc.):
  - Trigger is a fully rounded (`rounded-full`) pill: optional leading icon, selected label (or placeholder in gray), and a chevron that flips (`FiChevronDown` ↔ `FiChevronUp`) when open. Border goes to `border-gray-900` while open, `border-red-400` on error.
  - The options panel is a custom rounded-2xl card below the trigger (not a native listbox): each row can carry its own icon and an optional trailing `tag`, hover uses `hover:bg-gray-50`, and the selected row is highlighted `bg-indigo-50 text-indigo-700`.
  - Not a native form element — wire it into React Hook Form via `Controller`, same pattern as `DatePicker`:
    ```javascript
    <Controller
      name="gender"
      control={control}
      defaultValue=""
      render={({ field }) => (
        <Dropdown
          placeholder="Select gender"
          icon={<FiUser className="w-4 h-4" />}
          options={GENDERS.map((g) => ({ value: g, label: g }))}
          value={field.value}
          onChange={field.onChange}
          error={errors.gender?.message}
        />
      )}
    />
    ```
  - A toolbar/filter usage (already-controlled `value`/`onChange`, no form) just skips `register`/`Controller` and passes `value`/`onChange` directly.
  - For a long option list (100+ items — e.g. cities), pass `searchable` to render a small search box pinned to the top of the panel that filters options client-side. Don't render huge lists unfiltered.
- **Location fields (State/City)**: Never a free-text `Input` for State or City — always the dependent `Dropdown` pair, sourced from the `country-state-city` package via `lib/location.js` (`getIndianStates()`, `getCitiesForState(stateIsoCode)`), same dependent pattern as Class → Section:
  - `State` is `searchable`, keyed by ISO code locally (needed to look up its cities) but writes the human-readable state **name** into the form field via `field.onChange`.
  - Selecting a state resets `city` (`setValue('city', '')`) and repopulates the `City` dropdown, which stays `disabled` until a state is chosen — mirroring Class → Section.
  - This also fully avoids the browser's native address-autofill flyout ("Manage addresses…") that Chrome shows on free-text city/state inputs even with `autoComplete="off"`, because a `Dropdown` is a `<button>`-driven custom control, not a native text input, so there's nothing for the browser to autofill.
- **No native autosuggest**: Every text `Input` sets `autoComplete="off"` by default (baked into `components/Input.jsx`) so the browser's own autofill/autosuggest dropdown never appears over a field — callers can still opt back in by passing an explicit `autoComplete` prop when it's genuinely wanted (e.g. a password field for a password manager). For fields the browser aggressively treats as address/contact data (city, state, street), `autoComplete="off"` alone is not reliable in Chrome — use the custom `Dropdown`/`DatePicker` pattern instead of a native input wherever that applies.
- **Form width**: A data-entry page (Add/Edit Student, and similar full-page forms) uses the full available width of the content area — no artificial `max-w-*` centering wrapper — and its field grid is `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` (via the shared `FormSection`) so at least 3 fields sit per row on desktop. Elements that should always span the full row (photo upload, address line 1/2) use `sm:col-span-2 lg:col-span-3`.

### Client Component
Marked with 'use client' - use for interactivity, useState, event handlers.

```javascript
// components/LoginForm.js
'use client';

import { useState } from 'react';
import Button from './Button';
import Input from './Input';
import Form from './Form';
import { loginUser } from '@/lib/api';

export default function LoginForm() {
  const [formData, setFormData] = useState({ email: '', password: '' });
  const [error, setError] = useState('');

  const handleChange = (e) => {
    const { name, value } = e.target;
    setFormData(prev => ({ ...prev, [name]: value }));
  };

  const handleSubmit = async (e) => {
    e.preventDefault();
    try {
      await loginUser(formData);
    } catch (err) {
      setError(err.message);
    }
  };

  return (
    <Form onSubmit={handleSubmit}>
      {error && <p className="text-red-500">{error}</p>}
      <Input name="email" type="email" placeholder="Email" value={formData.email} onChange={handleChange} />
      <Input name="password" type="password" placeholder="Password" value={formData.password} onChange={handleChange} />
      <Button label="Login" variant="primary" />
    </Form>
  );
}
```

## Service Period (Staff Tenure)
- Any staff-type module (Teacher, and any future employee module) tracks tenure as a **pair of dates**, not just a join date: `joiningDate` (required) and `relievingDate` (optional — a DatePicker left blank means "still serving"). Both live on the same record, validated in `lib/schemas.js` (`relievingDate: z.string().optional().or(z.literal(''))`).
- The profile's overview cards show a single **"Service Period"** card formatting the pair as `Jun 1, 2019 – Present` or `Jun 1, 2019 – Mar 31, 2025` (`formatServicePeriod()` in `TeacherOverviewCards.jsx`) rather than separate "Joining Date"/"Relieving Date" cards — don't split it back into two cards for a new module without a reason to.
- Don't model this as an array of employment stints unless a module actually needs multiple hire/rehire periods — a single from/to pair is the default, per the standing principle against premature abstraction.

## Classes & Sections Module
- **No global Sections page.** The sidebar's "Classes & Sections" link (`/dashboard/classes`) is a single top-level entry — sections are managed *inside* a class, never as a separate nav item. `app/dashboard/classes/page.jsx` → grid of class cards; `app/dashboard/classes/[id]/page.jsx` → that class's sections; `app/dashboard/classes/[id]/sections/[sectionId]/page.jsx` → one section's overview + student preview. Don't add a `/dashboard/sections` route.
- **Academic Session drives everything via the URL, not client state.** `AcademicSessionSelector` calls `router.push('/dashboard/classes?session=...')`; `app/dashboard/classes/page.jsx` is a server component that reads `searchParams.session` (falling back to `ACADEMIC_SESSIONS[0]`) and refetches `getClassesForSession()` server-side. Don't reimplement this as a client-side filter over an already-fetched full list — the session is meant to scope the server query itself, matching how real multi-session data would work.
- **Data model** (`lib/classes.js`, same `globalThis` seed-survival pattern as `lib/students.js`/`lib/teachers.js`): a `Class` has `id, name, level, academicSession, status, subjects` (array of subject-name strings) — **no `classTeacherId` on `Class`**; a `Section` has `id, classId, name, academicSession, classTeacherId, room, capacity, boys, girls, status`. `boys`/`girls` are curated static numbers on the seed record (same convention as the fake aggregate stats in `getStudentStats()`/`getTeacherStats()`) — `studentCount` is *always derived* as `boys + girls` inside `decorateSection()`, never stored directly; don't reintroduce a separate stored `studentCount` field. The tiny real seed list in `lib/students.js` is only used for the section's **Student Preview** (matched live by `class`+`section`+`academicSession`), exactly like the small real seed arrays back the detail tables elsewhere while big dashboard-style numbers are hardcoded for a convincing demo. A brand-new section created through the UI starts at `boys: 0, girls: 0` (real enrollment isn't tracked per-gender by the Students module in this phase) — the form doesn't expose boys/girls as editable fields for the same reason it never exposed `studentCount`.
- **Class Level → Class Name is a strict derivation, not two independent fields.** `CLASS_LEVELS` (`lib/classes.js`) is `['Nursery', 'KG1', 'KG2', 'Prep', '1', '2', ..., '12']`; `classNameForLevel(level)` maps the four pre-primary levels (`PRE_PRIMARY_LEVELS`) to themselves unchanged and every numeric level to `` `Class ${level}` ``. `ClassFormModal` asks for **Level first** (a searchable `Dropdown`), then shows **Class Name second** as a disabled/`readOnly` `Input` whose value is computed live from the watched `level` field — the user never types a class name directly. `addClass`/`updateClass` re-derive `name` from `data.level` server-side too (never trust a client-sent `name`), so duplicate-class-name checking is really duplicate-*level*-per-session checking. Don't add a free-text class name field back — every level from Nursery to 12 must exist as a seeded/creatable class (see `SEED_CLASSES` covering the full range), and `lib/students.js`'s `CLASS_SECTIONS` (used by the Students/Teachers class dropdowns) mirrors the same range for consistency. ## Academic Sessions Module
- **Sidebar entry already existed** (`Academic Sessions` → `/dashboard/sessions`, `FiCalendar` icon) before this module had any pages behind it — don't add a second nav entry or duplicate icon; the route just needed to be built out.
- **Data model** (`lib/academicSessions.js`, same `globalThis.__ACADEMIC_SESSIONS__` seed-survival pattern as `lib/classes.js`): a session is `{ id, name, startDate, endDate, description, status, createdAt, updatedAt }` where `status` is one of `SESSION_STATUSES = ['Active', 'Upcoming', 'Archived']`. Stats (`studentCount`, `teacherCount`, `classCount`, `sectionCount`) are **never stored** — `decorateSession()` derives them on read by calling `getClassesForSession(session.name)` (reusing the Classes module's own aggregation) and filtering `getAllTeachers()` for any teacher with an assignment whose `academicSession` matches. This mirrors the Classes module's own "derive, don't store" rule for `studentCount`/`capacityState` — don't add stored counters that could drift from the underlying class/section/teacher data.
- **Session Name is auto-suggested, not required to be typed.** `suggestSessionName(startDate)` turns `2026-04-01` into `2026-27` (start year + two-digit next year). `SessionFormModal` watches `startDate` and calls `setValue('name', suggestSessionName(startDate))` on every change **until the user manually edits the Name field** (`nameTouched` state flips permanently on first `onChange`) — same "auto-fill until touched" pattern as `ClassFormModal`'s derived Class Name, except here the user *can* override it (unlike Class Name, which stays permanently derived/disabled) because a school might want a custom label like "Foundation Year" instead of a plain year range.
- **Only one session can be Active — this is enforced in the data layer, not just the UI.** `setActiveSession(id)` demotes whatever session currently has `status: 'Active'` to `'Archived'` before promoting the target, in the same function call — there is no intermediate state where two sessions are both Active or where the old active session becomes `'Upcoming'` again. `archiveSession(id)` explicitly throws if called on the currently-Active session ("Cannot archive the active session. Set another session as active first.") so the only path out of Active is `setActiveSession` on a different session.
- **Status is never a directly-editable form field.** `SessionFormModal` has no Status dropdown — a new session is always created as `'Upcoming'` (hardcoded in `addSession`), and editing an existing session (`updateSession`) only ever touches `name`/`startDate`/`endDate`/`description`, never `status`. The modal shows the current status as a read-only `StatusPill` instead. The only ways `status` changes are the dedicated `setActiveSession`/`archiveSession` actions (`SetActiveDialog`, the Archive `ConfirmDialog`) — don't add a Status `Dropdown` to the form.
- **Overlap and ordering are validated server-side in `lib/academicSessions.js`, not just in `academicSessionSchema`.** The Zod schema (`lib/schemas.js`) only checks `endDate > startDate` (client-side, instant feedback). `validateDates()` in `lib/academicSessions.js` re-checks that *and* calls `isOverlapping()` — any two sessions whose `[startDate, endDate]` ranges intersect are rejected with "This academic session overlaps with an existing session." — run by both `addSession` and `updateSession` (excluding the session being edited via `excludeId`). Duplicate session names (case-insensitive) are rejected the same way as duplicate class names in the Classes module.
- **`StatusPill` (`components/sessions/StatusPill.jsx`) is this module's shared dot-pill**, analogous to `StudentsTable`/`TeachersTable`'s locally-duplicated `StatusPill` — but since three status values (not two) are reused across `CurrentSessionCard`, `SessionCard`, `SessionDetailsHeader`, and `SessionOverviewCard` within the *same* module, it's one shared file here rather than copy-pasted per component: green dot for Active, blue for Upcoming, gray for Archived. A `size="lg"` variant (bigger text/padding/dot) is used only in `CurrentSessionCard`, the one place the pill needs to read as a prominent hero element rather than an inline table-style badge.
- **Session actions are gated by status**, matching the spec's action matrix — implemented via conditional rendering, not a single shared "all actions always visible, some disabled" menu:
  - **Active**: Edit button only, no `⋮` menu (nothing else applies while a session is active — you can't Set-Active-an-already-active-session or Archive it).
  - **Upcoming**: Edit button **and** a `⋮` `DropdownMenu` with "Set as Active" (opens `SetActiveDialog`) and "Archive" (danger-styled, opens the shared `ConfirmDialog`).
  - **Archived**: View only — no Edit button, no `⋮` menu. There is no "reactivate an archived session" action; going back to a past session as Active would need to go through `setActiveSession` on it directly if that's ever wanted, but the UI doesn't expose it today.
  - This same status-gated logic is duplicated between `SessionCard` (list view) and `SessionDetailsHeader` (detail view) rather than factored into one shared component, consistent with this codebase's per-surface self-contained-actions convention (`ClassCard`/`SectionCard` each own their own modals rather than lifting state to a parent).
- **`SetActiveDialog` is a bespoke dialog, not `ConfirmDialog`**, because the action is a positive/promotional one, not destructive — its confirm button uses the primary violet→blue gradient (matching `Button`'s `primary` variant), not `ConfirmDialog`'s red. It shows a `"2025-26 → 2026-27"` transition chip and an explanatory line ("2025-26 will no longer be the active session.") whenever another session is currently Active, matching the spec's exact wording; if there's no current Active session (edge case, e.g. right after seed data is cleared) it falls back to a simpler "`{name}` will become the active session." line instead. Archiving, by contrast, **does** reuse the shared `ConfirmDialog` with its red confirm button, since losing edit access to a session is closer to the other red-button actions (deactivate teacher/section) than to a positive promotion.
- **`CurrentSessionCard`'s gradient is a subtle background wash, not a colored card.** Per the spec ("don't make the entire card overly colorful"), the card itself stays white — the only gradient elements are a large `blur-3xl` soft violet/indigo/blue circle absolutely positioned in the top-right corner at low opacity, and the `FiCalendar` icon badge itself (`bg-gradient-to-br from-violet-700 via-indigo-600 to-blue-600`). Don't apply the gradient as the card's own background or border.
- **`SessionClassStructure` (session detail page) reuses the Classes module's own decorated `cls.sectionCount`/`cls.totalStudents`** (via `getSessionById()` calling `getClassesForSession(session.name)` and attaching the result as `session.classes`) rather than recomputing anything — each row is a `Link` straight into `/dashboard/classes/[id]`, so this page is a read-only lens into the Classes module for a given session, not a parallel data source. This is the same "session isolation" the spec calls for: whichever classes/sections/students/teacher-assignments carry that session's name in their own records are what show up here — there's no separate `sessionId` foreign key anywhere else in the codebase.
- **Empty state** (`SessionsEmptyState.jsx`) only renders when `sessions.length === 0` — with the seed data always containing three sessions this path isn't reachable through the UI today, but it's wired up correctly (same icon-badge-hero shape as other empty states in the app) for whenever a school's data is actually cleared.

## Attendance Module
- **New Sidebar group**: "Attendance" (`FiCheckSquare`) with two children — "Daily Attendance" (`/dashboard/attendance/daily`, the default landing page) and "Attendance Reports" (`/dashboard/attendance/reports`) — added to `components/dashboard/Sidebar.jsx`'s `NAV_ITEMS` right after "Classes & Sections," following the exact same `NavGroup` pattern as Students/Teachers. `/dashboard/attendance` itself just redirects to `/daily`.
- **Class 8-A and Class 9-A got a real, fuller roster specifically for this module** — `lib/students.js` gained 10 new seed students (ids `7`-`16`) bringing Class 8-A to 8 students and Class 9-A to 4, instead of the usual 1-2 real students per section elsewhere in the app. This was a deliberate scoping call: attendance needs an actual named roster to mark, unlike a passive stat card, and Class 8-A/9-A were chosen because they line up with teacher Rahul Kumar's (`lib/teachers.js` id `'1'`) existing assignments — which is also why the seeded "Attendance Already Marked" demo record and the Teacher-role demo both center on this same teacher/class pairing. Every other class/section keeps its original tiny (often zero) roster, which is *intentional* — it's what naturally exercises the "No students in this section" empty state without needing separate fake-data logic.
- **`lib/attendance.js` stores real marked-attendance records** (`globalThis.__ATTENDANCE__`, keyed by academicSession+date+className+sectionName, one admin-per-school-style singleton array) **but computes Reports numbers from a deterministic seeded PRNG, not stored history.** Generating and maintaining a real day-by-day row for every student since term start isn't practical for a seed dataset — `syntheticStatusFor(studentId, dateStr)` (a `mulberry32`-style seeded RNG hashed from `studentId|date`) fabricates a believable ~90% Present / 5% Absent / 3% Late / 2% Leave status for any (student, date) pair, stable across reloads. **A real saved record always wins over the synthetic fill for that exact session+date+class+section** (see `statusFor()`) — this is what keeps Daily Attendance and Reports honestly connected: mark today for real, and Reports immediately reflects it; every other day in a report's date range is synthetic. Don't be surprised that Reports numbers change slightly if the date range shifts — that's the PRNG, not a bug. Sundays are excluded from all date-range iteration (`dateRange()`) as a simple "school day" approximation; Saturdays are treated as full school days.
- **Attendance % is defined as `Present / (Present+Absent+Late+Leave)`, not counting Late/Leave as any partial credit** — verified against the module spec's own worked example (20 Present, 1 Absent, 1 Late, 0 Leave → 90.9%) which only matches this exact formula. `StudentAttendanceReportTable`'s "Good" vs "Needs Attention" badge threshold is `>= 85%` — deliberately just two labels with green/amber (no red), per the spec's "avoid excessive warning colors" instruction.
- **Role-based access is a real, demonstrable mechanism, not just a visual affordance — but it is a demo mechanism, not real per-request auth.** `lib/currentUser.js` holds one `globalThis`-cached `{ role, teacherId }` flag, flipped by which `RoleToggle` option (`Admin`/`Teacher`) was used at `/login` (`LoginForm.jsx` calls the new `setCurrentRole()` after either login path resolves) and reset to `SchoolAdmin` whenever a super admin uses "Manage This School." Choosing "Teacher" always maps to the same hardcoded demo teacher (Rahul Kumar) rather than a real selected identity — there's no per-browser-session distinction, so two people testing "Teacher" mode in the same running dev server share the same flag. `getCurrentUser()` returns `assignedClasses` (from that teacher's own `lib/teachers.js` assignments) which both `DailyAttendanceBoard` and the Reports page use to **structurally** restrict the Class/Section dropdowns (Teacher literally cannot select a class they're not assigned to — the option isn't in the list) rather than merely hiding a button after the fact. A `FiUserCheck` "Showing your assigned classes" badge appears next to the Daily Attendance/Reports headers whenever `role === 'Teacher'` for discoverability, since there's no visible role switcher anywhere else in the UI.
- **Daily Attendance is a fully client-driven board (`DailyAttendanceBoard.jsx`), not URL/searchParams-driven like Classes/Sessions** — this is a deliberate departure from that established convention: marking attendance needs to feel instant (the module's explicit "must be fast" core UX principle), so Session/Date/Class/Section changes trigger a client fetch (`GET /api/attendance/roster`) rather than a full page navigation. Reports, by contrast, **does** stay URL/searchParams-driven (`ReportsFiltersBar` builds a query string and `router.push`es on "Apply Filters") — matching the rest of the app, since a report is a stable, shareable/bookmarkable view rather than a rapid-fire marking workflow. Don't blur these two patterns together.
- **A freshly-loaded (never-saved) roster defaults every student to `Present`, not blank.** This was a deliberate resolution of tension between the spec's literal component order ("Mark All Present" presented as an explicit first step) and its core "must be fast" principle: defaulting everyone to Present means zero clicks are needed for the common case (most students attend), and "Mark All Present" becomes a one-click bulk-revert action instead of a mandatory first step — still genuinely useful after a teacher has made a few changes and wants to reset. If an existing record is loaded instead (see below), statuses come from that record, never from this Present-by-default rule.
- **"Attendance Already Marked" vs. the marking UI is a hard `isEditing` boolean switch, not two views rendered together.** `getAttendanceRecord()` returning non-null on roster load sets `isEditing = false` and shows `AttendanceAlreadyMarkedCard` (with the real `markedBy`/`markedAt` from the saved record) instead of the summary cards + table; clicking "Edit Attendance" flips to `isEditing = true` and pre-fills `statuses`/`remarks` from that record. Saving updates `existingRecord` in place and resets the dirty-tracking `baseline` but does **not** flip back to the summary card — you stay in the editor after a successful save, matching how the sticky action bar's Save/Reset buttons naturally disable once there's nothing left to save.
- **The sticky bottom `AttendanceActionBar`'s live Present/Absent/Late/Leave counts are always computed over the full roster**, never the search-filtered subset — search (`AttendanceFiltersBar`'s "Search Student" field) only hides/shows rows in `AttendanceTable`/`AttendanceMobileCards`, it never touches the underlying `statuses` map. Likewise, "Mark All Present" always applies to the entire roster regardless of an active search filter, for the same reason: a partially-filtered "mark all" would be a confusing, non-obvious scope for what reads as a global action.
- **Remarks use the same `Modal`-based small-form pattern as the rest of the app** (`RemarkModal.jsx`, mirroring `SubjectsModal`'s "small dedicated popup, not the full form" philosophy from the Classes module) — a single required textarea, no rich text, no per-student large inline textareas in the table. The Actions column's `DropdownMenu` label switches between "Add Remark" and "Edit Remark" based on whether that student already has one; there's no separate "Clear Remark" action (re-saving with different text just overwrites).
- **`components/attendance/statusStyles.js`** (`STATUS_META`) is this module's single source of truth for the Present/Absent/Late/Leave color+icon mapping (green/red/amber/blue respectively) — used by `StatusSegmentedControl`, `StatusPill`, `AttendanceActionBar`'s count dots, the Reports donut, and the Student Profile tab's recent-attendance list. Change colors/icons there once, not per-component.
- **`DonutChart` (`components/dashboard/DonutChart.jsx`) gained optional `centerValue`/`centerLabel` props** (defaulting to its original `{total} / Total` behavior when omitted) specifically so `OverallAttendanceDonut` could show "93.4% / Overall" in the center without duplicating a whole donut-chart component — this is a backward-compatible extension, the dashboard's own existing `StudentOverviewCard` usage is unaffected. Reach for this prop rather than overlaying a second absolutely-positioned label on top of `DonutChart`, which would visually double up with its built-in center text.
- **The Student Profile "Attendance" tab (`StudentAttendanceTab.jsx`) is the one piece of this module that fetches its own data client-side via a dedicated API route** (`GET /api/attendance/student/[id]?month=YYYY-MM`), rather than being fed data from the server-rendered profile page — this is what makes the "`[ August 2026 ▼ ]` for monthly filtering" requirement work without a full page reload per month change. `ProfileTabs.jsx`'s previously `comingSoon`-flagged "Attendance" tab is now live; "Exams" remains the one still-disabled `comingSoon` tab.
- **Multi-school/tenant isolation for Attendance is inherited from the existing single-tenant-singleton design, not newly built here** — Attendance reads `lib/students.js`/`lib/teachers.js`/`lib/academicSessions.js` exactly like every other module, so whichever school is currently "managed" via `lib/school.js`'s singleton is implicitly the only school Attendance ever shows. There is no per-school attendance data partitioning to speak of (same caveat as documented above for Schools/Admins) — this module doesn't attempt to solve that; it just doesn't make it any worse.

## Teacher Role Is Locked Down App-Wide (Attendance + Read-Only Own-Class Students Only)
Per explicit instruction: "Teachers only take attendance and able to view attendance and their students (respective class), won't be able to manage anything (edit/delete/modify)." Before this, Teacher-role scoping only existed inside the Attendance module (see above) — every other module (Teachers, Classes & Sections, Academic Sessions, School Settings, and all of Students' create/edit/delete) was fully open to anyone who logged in as a Teacher, since nothing checked `currentUser.role` outside Attendance. This closes that gap app-wide.

- **`lib/roleGuard.js` is the new shared enforcement point** — `blockIfTeacher(redirectTo)` is an async server-side check (call it as the very first line of a page/layout) that redirects a Teacher away before any restricted data is even fetched; `isStudentInTeacherScope(student, assignedClasses)` is the one place the "is this student in one of my class+section+session assignments" check lives, used identically by both the Students list (to filter) and the Student profile page (to 404 direct access to someone else's student). **Every restriction here is enforced at the page/layout level, not just by hiding a Sidebar link** — a hidden nav item alone doesn't stop someone typing the URL, so each blocked route was verified by direct navigation, not just by checking the Sidebar looks right.
- **Fully blocked for Teacher** (redirect to `/dashboard/attendance/daily`, or to the relevant Students page for the two Students-specific ones): `/dashboard` (the school-wide admin dashboard itself — `app/dashboard/page.jsx`), all of `/dashboard/teachers/*` (new `app/dashboard/teachers/layout.jsx`), all of `/dashboard/classes/*` (new `app/dashboard/classes/layout.jsx`), all of `/dashboard/sessions/*` (new `app/dashboard/sessions/layout.jsx`), all of `/dashboard/settings/*` (added to the existing `app/dashboard/settings/layout.jsx`), and specifically `/dashboard/students/add` + `/dashboard/students/[id]/edit`. A brand-new route segment under any of these four modules is automatically covered by its layout guard — don't add a redundant `blockIfTeacher()` call inside individual pages within an already-guarded module.
- **Students is the one module Teachers partially keep — view-only, scoped to their own classes.** `app/dashboard/students/page.jsx` and `.../[id]/page.jsx` both call `getCurrentUser()` and branch on `role`: the list is pre-filtered via `isStudentInTeacherScope` (not just hidden rows — a Teacher's `students` array literally never contains anyone else's students), the Class filter dropdown's own options are equally filtered, and the profile page 404s outright (not "renders read-only," `notFound()`) for a student outside scope. A `canManage` boolean (computed once as `currentUser.role !== 'Teacher'`) threads down through `StudentsHeader` (hides "Add Student"), `StudentsExplorer`→`StudentsTable` (hides the row-selection checkboxes and the entire Actions column, in both the desktop table and mobile cards — not just the dropdown items inside it) and `BulkActionsBar`, and `ProfileHeader` (hides "Edit Student" + the "⋮" Deactivate/Delete menu). Follow this same `canManage` prop-threading pattern if another partially-visible module is ever added for Teacher — don't invent a different flag name per module.
- **The Students list's stat cards are real counts for a Teacher, not the usual fake school-wide numbers.** `getStudentStats()` (school-wide, hardcoded per the documented "big numbers are curated demo data" convention) would show "1,248 Total Students" above a table that only actually lists ~50-80 rows for a Teacher — since that's actively misleading, not just inconsistent, `app/dashboard/students/page.jsx` computes real `{total, active, inactive}` from the Teacher's own already-filtered roster instead (`newAdmissions` has no reliable derivation from seed data, so it's just `0` for this view). Admins still see the original fake `getStudentStats()` numbers, unchanged.
- **Sidebar and Topbar both take an explicit `role` prop now** (threaded from `app/dashboard/layout.jsx`'s `getCurrentUser()` call, through `DashboardShell`), not inferred client-side. `Sidebar.jsx` picks between two entirely separate nav arrays — `ADMIN_NAV_ITEMS` (unchanged, full module list) and `TEACHER_NAV_ITEMS` (just Dashboard/Students/Attendance, and "Students" has no "Add Student" child since there's nothing to add) — rather than filtering one array with per-item role flags, since the Teacher list is short enough that a second explicit array is clearer than a filter predicate. `Topbar.jsx` hides "Manage Schools" (an admin/super-admin escape hatch a Teacher should never see) from the account dropdown and hides the decorative "Quick Report"/"Create New" buttons entirely for Teacher — those two aren't wired to any real functionality anywhere in the app, but per the "won't be able to manage anything" instruction they shouldn't visually suggest creation capability to a Teacher either.
- **What was deliberately left alone**: the Documents tab's per-document "upload" buttons (on both Student and Teacher profiles) are pre-existing non-functional stubs everywhere in the app, not something newly exposed to Teachers — they weren't specifically hidden for Teacher view since they don't do anything for any role today. ## Attendance Time-Limit & Lock/Unlock Permission Matrix
Implements the specific Teacher-vs-Admin rules the user gave as a table: Teachers can only mark today's attendance before a deadline and can only edit within a grace period after saving; Admins have no such limits and can override/unlock a Teacher's locked record. **Configurable by School Admin (School Settings) or Super Admin (via "Manage This School" into that same Settings page)** — there's no separate super-admin-only settings surface, per the user's "admin ya superadmin" ask; both reach the identical form because Super Admin's "Manage" flow lands them in the same `/dashboard` a school admin uses.

- **Two new settings live on the `lib/school.js` singleton**: `attendanceDeadlineTime` (`'HH:MM'`, default `'14:00'`) and `attendanceEditGraceMinutes` (default `30`). Editable from a new **"Attendance Rules"** tab in School Settings (`components/settings/AttendanceRulesForm.jsx`, 5th `SettingsNav` item) — a `Dropdown` of 30-minute time slots for the deadline and a `Dropdown` of common grace periods (15/30/45/60/90/120 min), not free-text inputs, to keep values well-formed without needing a custom `TimePicker` component.
- **`computeAttendanceAccess({ record, role, date, schoolSettings, now })` in `lib/attendance.js` is the single source of truth for the whole permission matrix** — pure and unit-testable (`now` is injectable). Returns `{ allowed, reason }`, not separate mark/edit booleans, because in this implementation "can mark" and "can edit" collapse to the same check: `!record` (fresh) checks the deadline-for-today rule, `record` present checks the grace-period-since-`markedAt` rule (or `record.manuallyUnlocked` bypassing it). **Admin (`role !== 'Teacher'`) always short-circuits to `{ allowed: true }`** — no deadline, no grace period, ever, matching "Admin: anytime" exactly.
- **Enforcement is server-side and authoritative, not just a disabled button.** `POST /api/attendance` (the save route) recomputes `computeAttendanceAccess` itself before writing and returns 403 with the human-readable `reason` if disallowed — the client-side gating in `DailyAttendanceBoard` (not rendering the marking grid, not entering `isEditing`) is there for UX speed, but a stale client (e.g. a Teacher who had the tab open before the deadline passed) is still stopped by the API. Don't trust `access.allowed` from an old fetch as permission to skip re-checking server-side if this logic is ever touched again.
- **`GET /api/attendance/roster` returns *two* access computations**: `access` (computed with the actual current viewer's role) and `teacherAccess` (the same computation forced to `role: 'Teacher'`, regardless of who's actually viewing). This is what lets an Admin — whose own `access.allowed` is always `true` — still see "this record is past the *teacher's* edit window" and get offered the unlock control, without needing a second round-trip.
- **`record.manuallyUnlocked` is the override/unlock mechanism** (Lock/Unlock row in the spec table) — a plain boolean on the saved attendance record, flipped via `PATCH /api/attendance/[id]/lock` (`{ unlocked: true|false }`), itself gated server-side to reject Teacher callers (`lib/currentUser.js`'s role check, same pattern as everywhere else in this app — a demo-level check, not real session auth). **Every fresh `saveAttendance()` call resets `manuallyUnlocked` back to `false`** — an admin's unlock is "spent" the next time anyone successfully saves that record, so it doesn't silently stay unlocked forever after being used once.
- **UI for this lives entirely in `AttendanceAlreadyMarkedCard.jsx`** (the already-marked summary screen, not the live-editing grid): when `!access.allowed`, the "Edit Attendance" button is replaced by an amber "Editing Locked" notice showing `access.reason` verbatim; when the viewer `isAdmin` (`currentUser.role !== 'Teacher'`) and `teacherAccess.allowed` is false (or the record is currently unlocked), a secondary "Unlock for Teacher" / "Re-lock for Teacher" button appears, calling `setAttendanceLock()` then `onLockChange` (a `loadRoster()` re-fetch, not local state mutation — keeps the two access computations authoritative). A **third** empty state (`AttendanceEmptyState` with a `FiLock` icon, "Attendance Marking Locked") appears instead of the marking grid when there's no record yet *and* `!access.allowed` — e.g. a Teacher picking a non-today date, or today past the deadline.
- **The "Teacher can only mark today" rule is date-based, not time-based, and doesn't apply to already-saved records.** Picking any non-today date with no existing record blocks a Teacher outright ("Teachers can only mark attendance for today"); the grace-period clock only ever starts from `markedAt` (the real save timestamp), regardless of what calendar date the attendance record is *for* — so backfilling rules and edit-window rules are deliberately independent, don't conflate them.

## Attendance Module: Dense Roster Grid Redesign (Post-Launch Revision)
The Daily Attendance marking surface described above was substantially redesigned after launch, in response to a user-supplied reference screenshot of a denser "click/keyboard-driven roster grid" pattern. The `AttendanceTable`/`AttendanceMobileCards` (desktop-table + separate mobile-card) approach from the original build was **deleted outright**, not kept alongside the new one — don't resurrect them or assume both patterns coexist.

- **A 5th status, `NA` ("Not Applicable"), was added** to `ATTENDANCE_STATUSES` in `lib/attendance.js` (order: `Present, Absent, Late, Leave, NA`) — for a student the day genuinely doesn't apply to (e.g. not yet enrolled), not a stand-in for Absent. `summarize()`'s percent calculation excludes NA from the denominator (`countable = total - summary.NA`) so marking someone NA neither helps nor hurts their attendance rate. The synthetic PRNG (`syntheticStatusFor`) still only ever produces the original four — NA only ever arises from a real, manually-saved record — so Reports/Student-Profile history essentially never shows it, which is expected, not a bug.
- **`STATUS_META` (`components/attendance/statusStyles.js`) is now the source of truth for *display* text, not just color** — each status has a `key` (the stored value: `'Present'|'Absent'|'Late'|'Leave'|'NA'`, unchanged, used for all data access like `summary.Leave`/`counts.Leave`) and a separate `label` (the shown text — `Leave`'s label is **"On Leave"**, `NA`'s is **"N/A"**). `StatusPill` renders `meta.label`, never the raw key. Also added: `shortLabel` (`P`/`A`/`L`/`LV`/`NA`, the 2-character grid-card badge text), `card` (the tinted background+border class for a roster card in that status), `STATUS_ORDER`, `nextStatus()` (cycles through `STATUS_ORDER`), and `STATUS_KEY_MAP` (`{p,a,l,v,n} → status`, the keyboard shortcut mapping — note `v` maps to Leave since `l` was already taken by Late).
- **`AttendanceRosterGrid.jsx` is the single component for both desktop and mobile** — a responsive CSS grid (`grid-cols-3` up to `xl:grid-cols-10`) of small numbered cards, no separate mobile layout needed. Each card is a `div[role="button"]` (not a real `<button>`, specifically so the small remark-icon `<button>` can be nested inside it without invalid HTML) showing roll number, a `shortLabel` status badge, and the student's name, tinted by `STATUS_META[status].card`.
  - **Click cycles status** via `nextStatus()` — this was a deliberate choice over "click opens a per-student status picker": cycling is faster for the common single-correction case and needs no extra UI, matching the module's core "must be fast" principle.
  - **Keyboard shortcuts operate on whichever card has DOM focus**: pressing `P`/`A`/`L`/`V`/`N` sets that exact status (not a cycle) via `STATUS_KEY_MAP`; `Enter`/`Space` cycles like a click. Cards are natively tabbable (`tabIndex={0}`), so Tab/Shift+Tab move between them.
  - **Typing digits jumps focus to that roll number**: `AttendanceRosterGrid` buffers keypresses matching `/^[0-9]$/` into a ref, debounced 500ms, then looks up the roll number in the `rollNumbers` map and calls `.focus()` on that card. Multi-digit rolls (e.g. "15") work because of the debounce — don't shorten that timeout without testing double-digit rolls.
  - **The remark affordance is a tiny icon in the card's bottom-right corner** (`FiMessageSquare`, `stopPropagation()`'d so it doesn't also trigger the cycle), gray when no remark exists and indigo when one does — there is no more "Actions" column/`DropdownMenu`, since the dense card has no room for one.

Search also matches a typed roll number now, not just name/admission ID.
- **`AttendanceSummaryPanel.jsx` (new) is a sticky right-hand sidebar** (`lg:sticky lg:top-6`, stacks below the roster on smaller screens via the parent's `grid-cols-1 lg:grid-cols-[1fr_280px]`) listing each status with its count/percent, expandable per-row (click a row to reveal the roll+name list of everyone currently in that status) — the `NA` row only renders at all once its count is above zero, keeping the panel uncluttered on the common case. It also carries the "Quick Keys" legend (click/letter-keys/digit-jump), which is the one place those shortcuts are documented in-app.
- **Top summary cards (`AttendanceSummaryCards.jsx`) grew from 5 to 6**, reordered to `Present, Absent, Late, On Leave, N/A, Total Students` (Total moved to last) to match the redesign reference. `AttendanceActionBar`'s sticky bottom counts row picked up the `NA` count automatically since it already iterates `Object.entries(counts)` generically — no direct edit needed there.
- **"Mark All Present" moved to the primary gradient button style** (was a lighter green `bg-green-50` button) and now shows a transient inline confirmation line ("All students marked as present.") beneath it for ~4 seconds (cleared early if the user makes any other change) — purely a `setTimeout`-managed piece of local state (`markAllFeedback`) in `DailyAttendanceBoard`, not a toast.
- **Class 8-A and 9-A's rosters were bulk-expanded** (`lib/students.js`) to 50 and 28 students respectively (up from 8 and 4) specifically so this dense grid has a realistic-sized section to demonstrate — see `generateBulkStudents()`/`buildBulkStudent()`, which cycle two fixed 40/30-entry name-pool arrays (`BULK_FIRST_NAMES`/`BULK_LAST_NAMES`) rather than hand-authoring ~66 individual bios. These are still full, schema-complete student records (a bulk student's own Profile page renders correctly), just generated rather than bespoke — unlike the original hand-authored `SEED_STUDENTS`, don't expect a bulk student's guardian/address/fee data to be individually meaningful, it's realistic-looking filler. IDs `17`-`58` are Class 8-A, `59`-`82` are Class 9-A; don't reuse that id range for anything else.
- **A pre-existing bug this revision fixed**: when editing an already-saved attendance record, students not present in that saved record's `records` array (e.g. because the roster grew after the save) now correctly default to `Present` instead of rendering with an undefined/blank status — `DailyAttendanceBoard.loadRoster()` seeds every roster student to `Present` first, *then* overlays the saved record's entries on top, rather than building the status map from the saved record alone.

## Backend Migration: Auth API on Postgres + Prisma
First real-database module: Super Admin login, School Admin login/logout, and the whole School-Admin-management CRUD (create/permissions/status/reset-password) that `/super-admin` already depended on — all previously `globalThis`-cached in-memory arrays, now backed by a local Postgres instance (`school_management_system` db) via Prisma. Teacher login and the `lib/currentUser.js` SchoolAdmin/Teacher dashboard-role toggle were **deliberately left untouched** (still in-memory) — this pass covers only the two "real credential" logins that already existed, per explicit scoping with the user.

- **Prisma is pinned to the stable `6.19.3` line, not the `latest`-tagged `8.0.0-rc.*`.** `npm install prisma`/`@prisma/client` resolves `"latest"` to an 8.x release candidate today (an unusual dist-tag choice upstream) that mandates ESM-only generated client output and a `prisma.config.ts` + driver-adapter (`@prisma/adapter-pg`) setup — a poor fit for this project's plain-CommonJS, JS-only, no-`tsconfig` conventions. Don't let a future `npm install prisma` bump past 6.x without checking this reasoning still holds; re-pin with `npm install prisma@6.19.3 @prisma/client@6.19.3 --save-exact` if it drifts.
- **`prisma/schema.prisma` uses the classic Prisma 6 shape** — `datasource db { url = env("DATABASE_URL") }` right in the schema (not split into a separate config file), `generator client { provider = "prisma-client-js" }`. Two models so far: `SuperAdmin` (id/email/passwordHash/name) and `SchoolAdmin` (id/schoolId/name/email/passwordHash/status/permissions Json/createdAt/lastPasswordResetAt). **`SchoolAdmin.schoolId` has no foreign key** — Schools (`lib/schools.js`) are still in-memory, so the relation is joined at the application layer (`lib/admins.js`'s `decorateAdmin`), not via Prisma's relations. Migrate `schoolId` to a real FK only once the Schools module itself moves to Postgres.
- **`lib/db.js` exports a `globalThis`-cached `PrismaClient` singleton** — same caching pattern this codebase already uses for every in-memory store, needed here for the same reason (Next dev's Fast Refresh would otherwise open a fresh Postgres connection pool on every hot-reload).
- **Passwords are bcrypt-hashed (`lib/auth/password.js`, `bcryptjs`, 10 salt rounds)** — the in-memory version stored plaintext; this is a real improvement, not just a lift-and-shift. `prisma/seed.js` (run via `npm run db:seed`, also wired as Prisma's own `db:seed` hook so `prisma migrate reset` re-seeds automatically) hashes and upserts the exact same demo accounts the login pages already advertise in their "Test credentials" boxes (`superadmin@edumanage.io`/`SuperAdmin@123`, `info@abcpublicschool.edu`/`Welcome@123`, `admin@greenwoodhigh.edu`/`Welcome@123`) — keep these three in sync across `prisma/seed.js` and the two "Test credentials" boxes (`SuperAdminLoginForm.jsx`, `LoginForm.jsx`) if either ever changes.
- **A real session now exists: `lib/auth/session.js`'s `edumanage_session` httpOnly JWT cookie** (`jose`, HS256, 7-day expiry, `JWT_SECRET` in `.env`), set by `createSession({role, id, ...})` on successful login and read back by `getSession()`. This is a genuinely new capability, not present in the old stub logins at all — but **nothing reads it yet**. `/dashboard/*` and `/super-admin/*` still have no route-level guard checking this cookie (same pre-existing gap documented under "Super Admin Login (Homepage)" above) — don't assume adding the cookie means routes are now protected; that's a separate follow-up the user hasn't asked for yet. `POST /api/auth/logout` clears it.
- **`lib/auth.js`'s `validateSuperAdminCredentials` and `lib/admins.js`'s `validateAdminCredentials`/CRUD functions are now server-only** (they import the Prisma client) — this broke two client components that had been importing constants out of the same files: `SuperAdminLoginForm.jsx` (imported `SUPER_ADMIN_TEST_CREDENTIALS` from `lib/auth.js` — fixed by inlining that display-only constant directly in the component instead) and `AdminsTable.jsx`/`SchoolAdminCard.jsx`/`AdminPermissionsModal.jsx` (imported `ADMIN_PERMISSIONS` from `lib/admins.js` — fixed by extracting `ADMIN_PERMISSIONS`/`ADMIN_STATUSES`/`defaultPermissions` into a new client-safe `lib/adminConstants.js` with zero Prisma/DB imports, which `lib/admins.js` now also imports from). **This is the general rule going forward**: any `lib/*.js` module that gains a Prisma import can no longer be imported from a `'use client'` component, even just for a plain constant — split shared constants into a Prisma-free sibling file before migrating a module, don't discover it via a build error.
- **`app/api/auth/super-admin-login`, `.../school-admin-login`, and the new `.../logout` route are the only route files that changed** — every other admin-CRUD route (`/api/admins/[id]/*`, `/api/schools/[id]/admin`) needed **zero changes**, because `lib/admins.js` kept its exact old function signatures and return shapes. This is the payoff of the "keep old function names/signatures" rule above — verify it held after any future module migration by re-testing routes you didn't touch, not just the ones you edited.
- **Verified end-to-end**: wrong password rejected (both logins), correct Super Admin login sets the cookie and redirects to `/super-admin/schools`, correct School Admin login sets the cookie + still calls `setActiveSchoolContext` and redirects to `/dashboard`, logout clears the cookie, and the full admin-management loop (create → reset-password → toggle a permission → deactivate → reactivate) round-trips through Postgres correctly via direct API calls. Dev server restarted afterward (same standing convention as every in-memory seed change) purely to clear its own module cache — Postgres data itself doesn't reset on a restart the way `globalThis` arrays do, which is the actual point of this migration.

## Auth APIs Converted to Server Actions (No More `/api/auth/*` Routes)
Every login/logout/role-toggle flow (`Super Admin`, `School Admin`, `Teacher`, the SchoolAdmin/Teacher dashboard-role toggle, and the forgot-password stub) moved from client-side `fetch('/api/auth/...')` calls to Next.js Server Actions in `app/actions/auth.js`. Motivation was a user request to stop these calls showing up as named, readable REST endpoints in the browser's Network tab — worth being precise about what this does and doesn't achieve (also explained inline in `app/actions/auth.js`'s header comment):

- **A network request never disappears** — any client→server call is visible in DevTools no matter the mechanism. What changes is *discoverability*: instead of a clearly-named `school-admin-login` request with a plain JSON body, the Network tab now shows a generic POST to the current page URL, using Next's internal encoded Action-call protocol. This is obscurity, not encryption — don't oversell it as a security fix. Real transport security is still whatever TLS/HTTPS the deployment uses.
- **`app/api/auth/*` no longer exists at all** — `school-admin-login`, `super-admin-login`, `teacher-login`, `set-role`, `forgot-password`, and `logout` route files were all deleted, not left dangling. `lib/api.js` lost its corresponding five functions (`loginSchoolAdmin`, `loginTeacher`, `loginSuperAdmin`, `setCurrentRole`, `requestPasswordReset`) — if a future auth-adjacent feature is added, extend `app/actions/auth.js`, don't recreate an `/api/auth/*` route as the default choice.
- **Server Actions return `{ error }` on expected failures (bad credentials, missing fields) — they do not `throw`.** This was a real bug caught during verification, not a style preference: Next.js redacts a thrown Server Action error down to an opaque digest for any caller in a **production** build (a security feature to stop leaking stack traces), so `throw new Error('Invalid email or password.')` looked correct in dev (full message reaches the client) but would have silently broken every login error message the moment this app is built for production. Every action in `app/actions/auth.js` returns `{ error: '...' }` instead, and every calling component checks `result.error` rather than using `try/catch`. Follow this pattern for any new Server Action that has an expected/user-facing failure mode — reserve `throw` for genuinely unexpected failures (e.g. the DB being unreachable), where digest-only redaction in production is actually the desired behavior.
- **The dashboard Topbar's "Logout" button was a latent no-op before this** — `handleLogout` just did `router.push('/login')` with no server call at all, so the `edumanage_session` cookie set by a School Admin login was never actually cleared. Fixed as part of this pass (`logoutAction()` now runs first) since it's the same auth surface — verified the cookie is present before and genuinely gone after.
- **This did not touch route-level protection** — same pre-existing gap noted elsewhere in this doc: nothing checks `edumanage_session` on `/dashboard/*` or `/super-admin/*`, Server Actions or not. Don't treat "auth calls are less discoverable now" as "routes are now protected."

## Student Profile Attendance Tab: Full Month Calendar Grid (Redesign) + a Real Timezone Bug Fix
The Student Profile's "Attendance" tab (`components/students/StudentAttendanceTab.jsx`) was redesigned from a stat-cards + "last 10 days" list into a full month calendar grid (Mon–Sun weeks, one status icon per day), per a user-supplied reference screenshot of a similar calendar-style attendance history view.

- **`lib/attendance.js`'s `getStudentAttendanceStats` now returns every calendar day of the requested month as `days: [{date, status}]`**, not a `recent` array capped/reversed to the last 10 entries — a full month grid needs a cell (and either a real status or `null` for "hasn't happened yet") for every day-of-month, not a truncated tail. `status` is `null` only for a day strictly after today; every day up to and including today gets a real status via the existing `statusFor()` synthetic-fallback chain, same as before.
- **`StudentAttendanceTab.jsx`'s `buildCalendarWeeks()` turns that flat `days` list into Monday-start week rows**, padding the first/last week with the neighboring month's overflow days (dimmed, no icon, no data fetched for them — a standard calendar-widget convention, not an attempt to show real cross-month data like the reference screenshot's padding cells did). Month navigation reuses the existing bounded 6-month `monthOptions()` list (prev/next arrows just move an index into it, clamped at both ends — there's no unbounded date navigation), plus a "Today" button that jumps back to index 0.
- **`STATUS_META` (`components/attendance/statusStyles.js`) gained an `iconText` field per status** (e.g. `Present: 'text-green-600'`) — needed for the calendar's white-circle summary chips, which color just the icon rather than using an existing `pill`/`card` background+text combo. This was a deliberate fix mid-build: the first draft computed `meta.dot.replace('bg-', 'text-')` at render time, which technically worked in dev but is a real bug — Tailwind's build-time class scanner only finds literal class-name strings in source, so a runtime-concatenated class like that would silently produce no CSS (and thus no color) in a production build. **Never construct a Tailwind class by string-manipulating another class at runtime** — add the literal class as its own field on the shared style object instead, like `iconText` here.
- **A real, pre-existing timezone bug surfaced (and was fixed) while building this**: `lib/attendance.js`'s `dateRange()` built a `Date` at local midnight (`` new Date(`${from}T00:00:00`) ``) and then read it back with `.toISOString().slice(0, 10)`. `toISOString()` always converts to UTC first — on a server running in a timezone ahead of UTC (this machine is `Asia/Calcutta`, UTC+5:30), local midnight rolls back to the *previous* UTC calendar day, so **every date this function produced was silently shifted back by one day**. This was invisible in the old "last 10 days" list (a list of dates doesn't expose gaps the way a fixed grid does) but immediately visible in the new calendar as a real day (e.g. Aug 1) rendering as empty/no-data. Fixed with a new exported `toLocalDateStr(date)` helper (reads `getFullYear()`/`getMonth()`/`getDate()` directly, no UTC conversion) and applied everywhere the same buggy pattern existed: `dateRange()`, `generateHistoricalAttendance()`, `SEED_ATTENDANCE_DATE`, `computeAttendanceAccess()`'s today-check, and the "today" defaults in both `app/dashboard/attendance/daily/page.jsx` and `app/dashboard/attendance/reports/page.jsx`. **If you add a new "today" or date-range default anywhere in the Attendance module, use `toLocalDateStr(new Date())` from `lib/attendance.js` — never `new Date().toISOString().slice(0, 10)`** — the latter is correct only for servers running at or behind UTC, and this app's dev server does not.
- Other `lib/*.js` modules (`lib/admins.js`, `lib/school.js`, `lib/schools.js`, `lib/academicSessions.js`) still have the same `toISOString().slice(0, 10)` pattern for their own "today"/`createdAt` defaults — **left untouched, out of scope for this fix**. They're lower-stakes (a one-day-off `createdAt` display date, not a data range with visible gaps) and belong to modules not currently being worked on; fix them the same way (`toLocalDateStr`) if and when a similar bug is reported there.

## IAM API: `GET /api/iam/me` — Unified "Who Am I" Endpoint, Session-Only (No localStorage)
Per explicit request: a dedicated IAM (identity) API for user info, backed entirely by the server-side session — the client never stores or reads identity itself, so there's deliberately nothing here that touches `localStorage`.

- **`lib/iam.js`'s `getCurrentUserInfo()` is the single resolution function** — it is what `GET /api/iam/me` calls, and also what server components (dashboard layout/pages) call directly (no internal HTTP round-trip needed just because a REST route also exists for external/client-side callers). Resolution order: read the `edumanage_session` JWT cookie (`lib/auth/session.js`) — `SuperAdmin` → `prisma.superAdmin.findUnique`, `SchoolAdmin` → `lib/admins.js`'s `getAdminById` (already decorated with `schoolName`); if there's no real session (or it points at a since-deleted account), fall back to `lib/currentUser.js`'s Teacher resolution, since `teacherLoginAction` doesn't set a real session cookie. Returns `null` (→ 401 from the route) only when none of those resolve.
- **This is layered on top of `lib/currentUser.js`, not a replacement for it** — every existing Attendance/Students role-scoping call site (`getCurrentUser()` from `lib/currentUser.js`) is untouched and still answers a different question ("which dashboard view/role-scoping should render"), not "what is this person's real name/email/school". Don't consolidate the two without checking every scoping call site first — they're deliberately separate concerns documented separately in this file.
- **A real bug caught by testing all three logins back-to-back in one browser session**: `teacherLoginAction` never touched `edumanage_session` at all, so a *stale* SuperAdmin/SchoolAdmin cookie from an earlier login in the same browser kept winning in `getCurrentUserInfo()`'s resolution order — logging in as a Teacher right after a SuperAdmin session would silently report back as the SuperAdmin. Fixed by adding `await clearSession()` to `teacherLoginAction` (`app/actions/auth.js`) before it sets the Teacher toggle. **Any future login action that doesn't itself call `createSession()` must still call `clearSession()`**, or it inherits whatever real session happens to be lying around from a previous login in the same browser.
- **Wired into the dashboard shell**: `app/dashboard/layout.jsx` now also calls `getCurrentUserInfo()` and passes it down as `userInfo` through `DashboardShell` → `Topbar`. `Topbar.jsx`'s account-menu trigger now shows real initials (`initialsFor(userInfo?.name)`, computed from first+second word, not sliced from a single word) plus the real name/email (email only rendered if present — Teacher's `userInfo` has none) next to the avatar, instead of a hardcoded "AD" badge with no name at all. **Falls back to the old "AD"-only look when `userInfo` is `null`** — the pre-existing gap where `/dashboard` is reachable without ever going through `/login` (no route guards yet, see "Super Admin Login (Homepage)" above) still exists; this doesn't newly break that case, it just doesn't show a name for it either.
- **`app/dashboard/page.jsx`'s greeting also switched from a hardcoded `"Admin"` to `userInfo.name`** — deliberately the **full** name, not `name.split(' ')[0]`, because a seeded admin like "Dr. Radhika Sharma" would otherwise greet as "Good morning, Dr." (caught during verification, not assumed). If a true first-name-only greeting is ever wanted, strip a leading title token (`Dr.`, `Mr.`, `Mrs.`, ...) explicitly rather than naively taking the first space-separated word.

## Pagination Component: Truncated Page Numbers (Was Rendering Every Page)
`components/Pagination.jsx` (shared by `StudentsExplorer.jsx` and `TeachersExplorer.jsx`) rendered a button for every single page with no truncation — fine at 2-3 pages, but a filtered list with enough rows (e.g. 82 results at `PAGE_SIZE = 5` → 17 pages) overflowed the pagination bar with 17 buttons in a row, wrapping badly. Reported with a screenshot showing exactly that.

- **New `getPageItems(page, totalPages, siblingCount = 1)` helper** always keeps page 1, the last page, and up to `siblingCount` pages on either side of the current page, collapsing any gap into a single `'...'` — the classic "1 … 4 5 6 … 10" pattern. - **`'...'` entries render as a plain non-clickable `<span>`, not a button** — they're purely visual gap markers, never a page you can jump to. Keyed by array index (`ellipsis-${index}`) since up to two can appear in the same render (one on each side of the current page) and neither has a natural unique value like a page number does.
- This is the one shared `Pagination` component in the app — fixing it here fixed both of its only two consumers (`StudentsExplorer.jsx`, `TeachersExplorer.jsx`) simultaneously; don't duplicate this truncation logic locally if a third consumer is ever added, import this component instead.

## New Modules: Notices and Homework
Two new full CRUD modules, requested together ("notice aur homework ka feature"). Both follow the established `lib/*.js` in-memory-store + Explorer/Card/FormModal component pattern (see Classes & Sections for the closest template) rather than introducing a new architecture — no new conventions were invented here, just applied to new entities.

### Permission model (confirmed with the user before building, not assumed)
- **Notices**: both Admin and Teacher can post. A notice's `audience` is either `'Whole School'` or `'Class'`. **Admin** can post either kind, targeting any class, and a `'Class'` notice's `sectionName` can be left blank to mean "the whole class, every section." **Teacher** can only ever post `audience: 'Class'` with both `className` and `sectionName` required, and that exact class+section must be one of their own assignments — the Audience dropdown is hidden entirely for a Teacher in `NoticeFormModal.jsx` (not just disabled) since there's no legal choice besides "Class" for them.
- **Homework**: both can create; Teacher scoped to their own assigned class+section (always a specific section, no "whole class" option — homework is inherently section-specific), Admin unrestricted, same shape as the Attendance module's permission split.
- **Both modules share one new scoping primitive**: `isClassInTeacherScope(assignedClasses, academicSession, className, sectionName)` in `lib/roleGuard.js` — a generalization of the existing `isStudentInTeacherScope` for a *submitted* class/section rather than an existing student record. Passing a falsy `sectionName` matches on class alone (any of the teacher's sections in that class) — used by Notices' "whole class" case; Homework always passes a real `sectionName` for an exact match. **Reuse this helper for any future module needing the same "is this class/section one of mine" check** — don't re-derive the `.some(...)` shape locally again.
- **Ownership for edit/delete**: `canManageNotice(currentUser, notice)` / `canManageHomework(currentUser, homework)` in `lib/notices.js`/`lib/homework.js` — Admin can always manage; a Teacher can only manage a record they themselves created (`postedByTeacherId`/`assignedByTeacherId` matches `currentUser.teacherId`). The "⋮" edit/delete menu is conditionally rendered per-card based on this (`NoticeCard.jsx`/`HomeworkCard.jsx`'s `canManage` prop, computed once in the Explorer and passed down) — a Teacher viewing a whole-school notice or another teacher's class notice sees no menu at all, verified with a second teacher account (Priya Sharma) seeing zero management affordances on Rahul Kumar's notices.
- **List visibility** (`getVisibleNotices(currentUser)` / `getVisibleHomework(currentUser)`) is separate from ownership: a Teacher *sees* whole-school notices and any class/section they're assigned to, but can only *manage* the ones they personally created — Admin oversight content (e.g. a homework Admin assigned to a Teacher's class) is visible to that Teacher but not editable by them, matching the "Admin: anytime, any class" / "Teacher: own class only" split from Attendance.
- **API routes accept a `currentUser` object as an explicit parameter into the `lib/notices.js`/`lib/homework.js` functions** (fetched by the route via `getCurrentActor()`, not called internally by the lib functions) — same pattern as `app/api/attendance/route.js` passing `role` into `computeAttendanceAccess()`. Validation failures (wrong scope, not the owner) throw a plain `Error('message')`, caught by the route and returned as a 400 — consistent with every other CRUD module in this app (`academicSessions.js`, `classes.js`, etc.).

### A real bug caught mid-build: posted-by name showed "Admin", not the real admin
The API routes originally called `lib/currentUser.js`'s `getCurrentUser()` for the acting user — correct for the Teacher case (that function already resolves the real teacher name from `lib/teachers.js`), but for SchoolAdmin it returns the generic hardcoded `name: 'Admin'` placeholder that function has always used, since it predates the real IAM/session work (see "IAM API" section above). Caught immediately by testing: a notice posted as Dr. Radhika Sharma showed "Admin" as the author.

- **Fixed with a new `getCurrentActor()` in `lib/iam.js`** — returns `lib/currentUser.js`'s exact shape (so `role`/`teacherId`/`assignedClasses` still work everywhere unchanged) but overrides `.name` with the real signed-in name from `getCurrentUserInfo()` when one exists and the role isn't `'Teacher'` (Teacher's name was already correct, no need to touch it). **Use `getCurrentActor()` (not `getCurrentUser()`) anywhere a real person's name gets written onto a new record** — this is now the case for Notices' `postedByName` and Homework's `assignedByName`, and should be the default choice for any future "who did this" field, not just role-scoping decisions (which still correctly use plain `getCurrentUser()`).

### Other implementation notes
- **`toLocalDateStr` (from `lib/attendance.js`) is reused for both modules' `createdAt`/`assignedDate` fields** — deliberately, to avoid reintroducing the exact timezone bug documented earlier in this file (`.toISOString().slice(0, 10)` rolling back a day on this Asia/Calcutta server). `HomeworkCard.jsx`'s client-side "is this overdue" check uses its own tiny local-date helper for the same reason, comparing `dueDate` and "today" as plain `'YYYY-MM-DD'` strings (lexicographic comparison, no `Date` parsing at all) rather than risk a timezone-related off-by-one on the overdue badge.

## DatePicker: Fixed a Forced-Scroll Bug Inside Modals (Portal + Fixed Positioning, Like DropdownMenu)
Reported with a screenshot: opening the calendar on the Notice modal's "Expiry Date" field made the whole modal scroll down, and the calendar rendered detached/overflowing below the visible card instead of sitting neatly under its input.

- **Root cause**: `DatePicker.jsx`'s calendar panel was `position: absolute` inside its own `relative` wrapper, which itself lives inside `Modal.jsx`'s `max-h-[90vh] overflow-y-auto` scrollable body. An absolutely-positioned element still counts toward its nearest scrollable ancestor's content height — so a calendar opening near the bottom of a modal (little space below the trigger) grew that scrollable area and forced it to scroll, rather than just rendering wherever there was room.
- **Fixed with the exact same technique `components/DropdownMenu.jsx` already uses for this identical class of bug**: compute the trigger button's `getBoundingClientRect()`, decide open-up vs open-down based on available space below (`PANEL_HEIGHT_ESTIMATE = 340`, a rough estimate of the day-view panel's rendered height — good enough since the flip only needs to be roughly right, not pixel-perfect), then render the panel via `createPortal(..., document.body)` at `position: fixed` coordinates. A portaled, fixed-position element is completely outside any ancestor's scroll/overflow accounting, so it can never again force a parent container to grow.
- **Click-outside detection now checks both `buttonRef` and a new `panelRef`** (the portaled panel's root) — previously a single `containerRef` wrapped both the button and the (non-portaled) panel, so one ref sufficed; once the panel moved out to `document.body` via the portal, it's no longer a DOM descendant of the button's wrapper, so outside-click logic needs to explicitly allow clicks on either.
- **Position also recomputes on scroll/resize while open** (`window.addEventListener('scroll', computePosition, true)` — capture phase, so it fires for scrolling inside `Modal`'s own `overflow-y-auto` body too, not just window-level scroll), matching `DropdownMenu`'s existing behavior, so the calendar tracks its input correctly if the surrounding page/modal scrolls for any other reason while it's open.
- **This fix is app-wide, not Notices-specific** — `DatePicker.jsx` is a shared primitive used in Academic Sessions' form, Attendance Reports' From/To fields, Student fee-date fields, and now Notices/Homework's date fields. Verified it still behaves correctly in a non-modal context too (Attendance Reports' inline filter bar) — same position-right-below-the-input behavior as before, just now portal-rendered.

## Correction: The Dropdown/DatePicker Positioning Fix Was Incomplete — Fixed Properly Now
The portal + fixed-position fix documented in the two sections above stopped the forced-scroll bug, but introduced a worse-looking new one: both `Dropdown.jsx` and `DatePicker.jsx` decided open-up vs open-down (and, when opening up, *where* exactly to place the top edge) using a single guessed constant height (`PANEL_HEIGHT_ESTIMATE`, 320/340px) — reasonable for a long option list, badly wrong for a short one. A 3-item Priority dropdown or a 2-item Audience dropdown is nowhere near 320px tall, so the flip logic routinely decided "not enough room below" when there was plenty, and then positioned the panel's top edge a full 320px above the trigger — leaving a large blank gap where the *guessed* panel would have been, with the small *actual* panel floating in that gap, overlapping completely unrelated fields above it (reported with screenshots: a Priority dropdown rendering on top of the Title field, an Audience dropdown the same). This shipped as "fixed" and wasn't — flagged directly by the user ("what the hell, are u joking or what?"), rightly.

- **Real fix: measure the panel's actual rendered height, don't guess it.** Both components now do a two-pass open: `handleToggle`/`openPicker` sets a provisional "open below" position immediately (so the panel has *something* to render at on its very first paint), then a `useLayoutEffect` — which runs synchronously after the DOM updates but *before* the browser paints, so this correction is never visible as a flash/jump — re-measures `panelRef.current.offsetHeight` (now the panel actually exists in the DOM with real content) and recomputes the true position from that real height. The `useLayoutEffect` also re-runs when the measured content can change size while still open: `Dropdown.jsx` on `filteredOptions.length` (typing into the search box grows/shrinks the list), `DatePicker.jsx` on `view` (day view and year view render at different heights).
- **`DropdownMenu.jsx` (the "⋮" actions menu) was already correct and needed no change** — it computes `items.length * ITEM_HEIGHT + 8`, which is an *exact* height, not a guess, because every menu item is a plain fixed-height row with no variable content (no search box, no scrollable clamp). The flaw was specific to `Dropdown`/`DatePicker`, whose panels have genuinely variable rendered height (a `max-h-64` scroll clamp, an optional search bar, differing calendar views) that a single constant can't represent for every instance.
- **Lesson for any future "where should this floating panel go" logic in this app**: if the panel's content height is fixed/computable in advance (like `DropdownMenu`'s uniform rows), a formula is fine and simpler than measuring. If it varies by instance or content (option count, search state, view mode), **measure the real rendered height via a ref in `useLayoutEffect`, don't estimate it** — an estimate that's "close enough" for the common case will be visibly, confusingly wrong for the cases that differ most from that estimate, which are exactly the cases most likely to get reported as broken.
- **Re-verified against the exact three scenarios from the bug report**: Section dropdown (4 options) in an Edit Notice modal, Audience dropdown (2 options), and Priority dropdown (3 options) — all three now open tightly anchored directly below (or above, if genuinely out of room) their own trigger, with no gap and no overlap with unrelated fields.

New module built straight onto Prisma (no in-memory phase — there was no legacy `lib/fees.js` to migrate from), following `Student`'s exact conventions: `schoolId` FK, `cuid()` ids, scoped via `getActiveSchoolId()`, `findFirst({ id, schoolId })` for lookups. - **Class/session referenced by name string, not FK** (`className`, `academicSession` fields) — matches how `Student.class`/`Student.academicSession` already work, and how `lib/classes.js`'s in-memory Class store has no real relational integrity to FK against anyway.
- **The core invariant this module is built around**: `StudentFeeItem` rows are copied from `FeeStructureItem` at generation time (`generateStudentFees` in `lib/fees.js`), never referenced live. Editing or fully deleting a `FeeStructure` afterward never touches an already-generated `StudentFee` — verified end-to-end: deleted a structure entirely, confirmed a student's already-paid `StudentFee` (status, total, all 4 items) was completely unaffected.
- **No partial payments in this MVP** — `collectManualPayment` always sets `paidAmount = totalAmount` and `status = PAID` in one `$transaction` with the `Payment` row it creates, exactly matching Rule 5/7. Manual collection only accepts `CASH`/`UPI`/`BANK_TRANSFER` — `RAZORPAY` is rejected server-side (that method only ever gets set by the not-yet-built payment-verification flow).
- **`generateStudentFees(feeStructureId, quarter)`** targets every `Active`-status student in that structure's `className`+`academicSession`, skipping (not erroring on) students who already have a `StudentFee` for that session+quarter — the `@@unique` constraint is the real source of truth, the pre-check just avoids a noisy `P2002` per already-done row and lets the response report `{ generatedCount, skippedCount, totalEligible }` for a useful toast message. Confirmed idempotent: running it twice on the same quarter generates 0 new records the second time.
- **UI**: new "Fees" sidebar group (admin-only, not in `TEACHER_NAV_ITEMS` — financial/administrative, same precedent as the pre-existing Fees student-profile tab already being admin-only) with Fee Structures / Student Fees / Payments pages. `StudentFeeQuarterCard.jsx` is the one shared presentational component rendered identically on the admin Student Fees page and the Student Profile's Fees tab, so a fee always looks the same wherever it's shown.

## Razorpay Standard Checkout Integration

Wires the "Pay Online" path into the Fees module (see the Phase 1-5 section above) — order creation, the Standard Checkout modal, and server-side signature verification. Webhook (idempotent `payment.captured`/`payment.failed` handling) is **not** built yet — this task was scoped to create-order/checkout/verify only.

- **`lib/razorpay.js`** — a `Razorpay` SDK client singleton (same `globalThis`-cache pattern as `lib/db.js`) plus `verifyRazorpaySignature()` (`crypto.timingSafeEqual` over the HMAC-SHA256 hex digest, not a plain `===`, to avoid a timing side-channel).
- **A real bug this surfaced**: `lib/fees.js` imports `lib/razorpay.js` at module scope, which calls `new Razorpay(...)` on load. Four client components imported plain constants (`FEE_QUARTERS`, `QUARTER_LABELS`) from `lib/fees.js`, which pulled that whole import chain into the browser bundle — crashing every Fees page client-side with `key_id is mandatory` (the secret is correctly never sent to the browser, so the client-side `new Razorpay()` call had nothing to authenticate with). Fixed by extracting those constants into a new dependency-free `lib/feeConstants.js`; `lib/fees.js` re-exports them for server-side convenience, but client components now import directly from `lib/feeConstants.js`. **Lesson for any future module split like this**: a "just constants" export from a file is not safe to import client-side if that same file also does server-only work at module scope (DB clients, SDK clients, secrets) — split the constants out, don't rely on tree-shaking to save you.
- **The amount is only ever set server-side**: `createRazorpayOrder(studentFeeId)` reads `StudentFee.totalAmount` from Postgres and creates the Razorpay order for exactly that — the client sends only a `studentFeeId`, never an amount. This makes the "incorrect payment amount" edge case structurally impossible rather than something to detect after the fact — a valid signature already proves the payment matched the order this route created, and that order's amount was never client-controlled.
- **`verifyRazorpayPayment`** checks, in order: (1) the fee exists, (2) a `Payment` row exists for that exact `studentFeeId` + `razorpayOrderId` pair (rejects an order id that's real but belongs to a *different* fee), (3) idempotency — if that `Payment` is already `SUCCESS`, returns the existing result with `alreadyProcessed: true` instead of reprocessing, (4) the HMAC signature, only then updating `Payment`→`SUCCESS` and `StudentFee`→`PAID` in one `$transaction`. A `P2002` on `razorpayPaymentId` (a second race-condition request recording the same payment id first) is caught and treated as the same idempotent-success case, not an error.
- **`components/fees/RazorpayPayButton.jsx`** — loads `https://checkout.razorpay.com/v1/checkout.js` via `next/script` (Next dedupes repeated `<Script>` tags with the same `src` automatically, so this is safe to render once per visible quarter card). Prefills `contact`/`email` from the student's guardian info where available — without it, Razorpay's checkout inserts an extra "enter your mobile number" step. `payment.failed` and the modal's `ondismiss` are both handled distinctly from a successful `handler` callback.
- **New env vars**: `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` (server-only) and `NEXT_PUBLIC_RAZORPAY_KEY_ID` (safe to expose — it identifies the account, not a credential) — `.env` was already gitignored (`.env*`), no change needed there.
- **Verified against the real Razorpay test-mode API** (not mocked): confirmed the provided credentials directly via `curl` before wiring anything up (a first credential pair was genuinely invalid — Razorpay's own API returned `401 Authentication failed` independent of any app code, caught before it wasted time debugging the wrong layer). With working credentials: order creation returns a real `order_...` id, the Standard Checkout modal opens with the correct branding/amount/prefilled contact, test card `4111 1111 1111 1111` is accepted. Full server-side verify path exercised by computing a genuine HMAC-SHA256 signature with the real key secret (Razorpay's hosted checkout UI is intentionally hardened against browser automation, so completing the *hosted* OTP step via Playwright wasn't reliable — verifying the signature-check logic directly, the same way Razorpay's own callback would, is the correct way to test the part our code is actually responsible for). Confirmed: valid signature → `PAID`; invalid signature → `400`, fee stays `PENDING`; missing fields → `400`; an order id that belongs to a different fee → `400`; creating a new order for an already-paid fee → `400`; a duplicate verify call on an already-`SUCCESS` payment → `200` with `alreadyProcessed: true` and no second `Payment` row created.

## Parent Portal (New Role) — View & Pay Own Child's Fees Online

Addresses a real gap the Fees module surfaced: "Pay Online" only ever lived in the admin panel because there was no parent/student login at all — an admin paying on a parent's behalf isn't how this should really work. This adds a fourth role (SuperAdmin/SchoolAdmin/Teacher were the only three before) with a real per-request session, since — unlike every other login here — a parent's identity is the only thing standing between them and another family's financial data.

- **`Student.portalPasswordHash`** (new, nullable) — authenticates against `Student.portalEmail`, which already existed on the model for exactly this (previously unused: no portal existed to log into). Most students never get one; a school admin issues it per-student via a new "Set Portal Access" item in `ProfileHeader.jsx`'s dropdown (`SetPortalAccessDialog.jsx`, same reveal-once-then-never-again pattern as `ResetPasswordDialog.jsx`) — `POST /api/students/[id]/portal-access` → `lib/students.js`'s `setParentPortalPassword`.

Unlike Teacher's `lib/currentUser.js` global toggle (fine for a single-admin demo persona, since only one person is ever "the" teacher at a time in this app), multiple real parents could be signed in as different people simultaneously, so this needed a real per-request identity from the start — `lib/iam.js`'s `getCurrentUserInfo()` gained a `Parent` branch, and a new `requireParent()` guard alongside the existing `requireSuperAdmin()`.
- **The one area of this app with real auth enforcement, on purpose** (at the time this was written — see "Teachers Module Migrated to Postgres" below for a later addition to this list): every other module documented in SKILL.md deliberately has no per-route auth check (single-admin-persona demo, no external threat model — see "Auth / Authorization" notes throughout). ## Teachers Module Migrated to Postgres; `Student`/`Teacher` Tables Renamed; New `requireSchoolAdmin()` Guard

Per explicit request, `lib/teachers.js` moved from its `globalThis`-cached in-memory array (the same "reset on every dev-server restart" gap that caused a real support issue — see below) to real Postgres rows, following the exact `lib/students.js` migration pattern (`decorateTeacher`/`buildTeacherFields`, per-school via `schoolId`, nested one-off groups as `Json`). Same request also asked for the underlying DB table names to read `Students`/`Teachers` (plural), and for auth checks to be added "wherever they should exist."

- **What surfaced this**: a user report of "teacher login shows invalid email/password even with the right demo credentials" traced back to `lib/school.js`'s `SCHOOL` singleton — the "active school" driving every per-school in-memory store (`lib/schoolScope.js`) is a single `globalThis` value, not per-session, so a Super Admin's "Manage This School" on a *different* school at any point during that server process's life silently emptied the Teacher/Student stores for everyone until a restart. Migrating to Postgres doesn't remove that singleton (it's unrelated), but it does fix the specific complaint that prompted this: teacher rows no longer reset on a dev-server restart the way the in-memory array did.
- **`prisma/schema.prisma`'s new `Teacher` model** mirrors `Student`: `education`/`bankDetails`/`emergencyContact`/`address` stay `Json` (nothing queries into them independently), and so does `assignments` (a plain array of `{id, academicSession, class, section, status}` — `lib/iam.js` only ever reads a teacher's own list wholesale, never queries "who teaches Class 8B" across teachers, so a real join table would add nothing). **Login credentials are the one place this deliberately does NOT mirror the old in-memory shape**: the old `loginAccess.password` (plaintext, inside the same Json blob) is now `loginPasswordHash` (bcrypt, its own column) plus separate `loginEnabled`/`loginEmail`/`loginAccountStatus` columns — same convention as `SchoolAdmin.passwordHash`/`Student.portalPasswordHash`. `decorateTeacher()` still hands callers back a `loginAccess: {enabled, email, role, accountStatus}` object (no `password` field, same as before — no caller ever read it) so **zero changes were needed in any API route or component**, per the established "migrated module keeps its old exported function names/signatures" rule.
- **`lib/teacherSeedData.js`** (new) holds the plain demo-roster data, same split as `lib/studentSeedData.js` — `prisma/seed.js` imports it and hashes each teacher's plaintext demo password (`Teacher@123`, etc.) before writing `loginPasswordHash`; nothing ever writes the plaintext value itself to Postgres.
- **`Student`/`Teacher` tables renamed to `Students`/`Teachers`** via `@@map("Students")`/`@@map("Teachers")` on the Prisma models — **the model identifiers themselves stay singular** (`model Student`, `model Teacher`), so `prisma.student.*`/`prisma.teacher.*` call sites in `lib/students.js`/`lib/teachers.js` needed zero changes; only the physical SQL table name changed. Done via a direct `ALTER TABLE ... RENAME TO ...` (through a one-off Prisma `$executeRawUnsafe` script), **not** `prisma migrate dev` or `db push --accept-data-loss` — this database's migration history was already drifted from its actual schema before this task (untracked earlier changes applied via `db push`), so `migrate dev` was refusing to run without a full `migrate reset` (which drops all data). Renaming the tables directly and then confirming `prisma db push` reports zero drift afterward was the non-destructive path; **any future schema change to this database should expect the same drift warning and should default to `db push` (never `migrate reset`) unless the user explicitly accepts a full local data wipe.**
- **New `requireSchoolAdmin()` in `lib/iam.js`**, alongside the existing `requireSuperAdmin()`/`requireParent()` — now guards every Teachers/Students management route (`/api/teachers`, `/api/teachers/[id]`, `/api/teachers/[id]/status`, `/api/teachers/[id]/reset-password`, `/api/teachers/[id]/assignments`, `/api/students`, `/api/students/[id]`, `/api/students/[id]/portal-access`, `/api/students/bulk-import`). Accepts a real session with role `SchoolAdmin` **or** `SuperAdmin` — the latter because `app/api/schools/[id]/manage/route.js`'s "Manage This School" flow only flips `lib/currentUser.js`'s dashboard-role toggle to `'SchoolAdmin'`, it never upgrades the real `edumanage_session` cookie, so a Super Admin who's stepped into a school still carries a real `SuperAdmin` session and would otherwise be locked out of the very module they stepped in to manage. Rejects: no cookie at all, a `Parent` session, and — notably — a browser sitting in the web dashboard's Teacher login, because `teacherLoginAction` (`app/actions/auth.js`) only flips the same in-memory toggle and never sets a real session cookie (only the mobile `/api/auth/teacher/login` route does), so `getSession()` correctly resolves to `null` there, same as a fully unauthenticated request.
- **Deliberately left unguarded** (at the time this was written — Classes was added next, see below): `GET /api/students/bulk-import/template` (a static sample `.xlsx` with no real data, downloadable by anyone) and every other still-in-memory module (Notices, Homework, Houses, Academic Sessions, Fees' non-Parent routes) — this pass was scoped to Teachers+Students specifically (per explicit request), not a full-app auth sweep. Those modules still rely entirely on `blockIfTeacher()`'s page-level redirect, same pre-existing gap as before; extend `requireSchoolAdmin()` to their routes the same way if asked.
- **Verified end-to-end**: unauthenticated `GET /api/students` and `POST /api/teachers` both now return `403 {"error":"Forbidden"}`; a hand-signed `SchoolAdmin` session JWT (via `signSessionToken`, same helper `createSession` uses) successfully reads `/api/students`; teacher login (`rahul.kumar@edumanage.com` / `Teacher@123`) succeeds against the new Postgres-backed `validateTeacherCredentials` and a wrong password is rejected; add/assign-class/status-update/reset-password all round-tripped through Postgres via direct API calls (test teacher created and cleaned up afterward); table rename confirmed non-destructive (`prisma.student.count()`/`prisma.teacher.count()` unchanged before/after, `prisma db push` reported zero drift post-rename); `/dashboard/teachers`, `/dashboard/students`, `/dashboard/students/list` all still render correctly.
- **Two real bugs caught by real usage after this shipped, both fixed the same session**: (1) `Teacher.dob` had no default and the "Add Teacher" form's Date of Birth field is genuinely optional (`lib/schemas.js`'s `teacherSchema`, no asterisk in `TeacherForm.jsx`) — submitting without one threw a Prisma validation error surfaced to the user as a generic "Failed to save teacher." Fixed with `dob String @default("")`, same convention as every other optional `Teacher` field. **Any column backing an optional form field must get a Prisma default (or be nullable) — cross-check the zod schema's `.optional()`s against the Prisma model's required fields whenever migrating a module, don't assume they already agree.** (2) `addTeacher()` never generated a login password even when "Login Access" was checked at creation — a school admin had to separately visit the teacher's profile and click "Reset Password" before that teacher could actually sign in. Fixed: `addTeacher()` now generates+hashes a temp password whenever `loginAccessEnabled` is set, returns it once (`{ ...decorateTeacher(row), tempPassword }`), and `AddTeacherForm.jsx`'s success screen reveals it the same way `ResetPasswordDialog.jsx` does (shown once, never stored in plaintext, never shown again).

## Classes & Sections Module Migrated to Postgres

Per explicit request ("classes and sections ki api banao sari"), `lib/classes.js` moved from its `globalThis`-cached in-memory arrays to real Postgres rows — same pattern as the Students/Teachers migrations above, plus one upgrade the other two didn't get.

## Attendance Module Migrated to Postgres

Per explicit request, `lib/attendance.js` moved from its `globalThis`-cached in-memory arrays to real Postgres rows — same overall pattern as Students/Teachers/Classes, with one deliberate design change forced by the move from an in-memory array to a real database.

- **New `Attendance` model** (table mapped to `Attendance` via `@@map`, same convention as every other migrated module) — **one row per class+section+date** (an actual saved marking session), not one row per student per day. `records` (a `Json` array of `{studentId, status, remark}`) stays exactly that shape, same as `Teacher.assignments` — nothing ever queries into an individual student's entry independently of the (date, className, sectionName) session it belongs to, so normalizing to one row per student per day would multiply row count by class size for zero query benefit.
- **The historical/seed data was intentionally dropped, not ported over** — the old `generateHistoricalAttendance()`/`SEED_ATTENDANCE` produced ~6 fabricated days of "real" records per class using hardcoded numeric student ids (`'1'`, `'3'`, `'7'`-`'12'`, ...) from before the Students migration; those ids stopped resolving to anything the moment Students moved to Postgres cuids, so the seed was already silently broken before this task. Rather than re-author it against real (and constantly-changing, per this session's own testing) student/teacher ids, this migration leans entirely on the existing `syntheticStatusFor()` deterministic-PRNG fallback for any (student, date) pair with no real saved `Attendance` row — which is also exactly what happened for every day *without* a seed row even before this migration, so this doesn't change the app's actual observable behavior (Reports/the Student Profile calendar still show a believable status for any past day), it only removes a handful of fabricated "real" rows for days nobody actually marked.
- **The one real design change, forced by moving off an in-memory array**: the old `statusFor(student, dateStr, academicSession)` was called once per (student, date) pair inside nested loops across every reporting function, doing a cheap `ATTENDANCE.find()` against an already-fully-loaded-in-memory array each time — fine for a JS array, but one Postgres round-trip per (student, date) pair would make a month-long class report issue hundreds of queries. Replaced with **`fetchAttendanceMap()`**: one `prisma.attendance.findMany()` per report call, scoped to the requested `academicSession` + date range (and `className`/`sectionName` where the caller already knows them, e.g. the Student Profile's single-student stats), building an in-memory `Map` keyed by `` `${date}|${className}|${sectionName}` ``. **`statusFromMap()`** (synchronous, no longer `async`) does the actual per-student lookup against that pre-fetched map, same fallback-to-synthetic behavior as the old `statusFor`. **Any future migrated module with a similar "loop over many (entity, date) pairs calling a per-pair lookup" shape should follow this same batch-fetch-then-map pattern**, not a query-per-iteration — the nested-loop shape that was fine against an in-memory array is a real N+1 query bug against a real database.
- **Authorization deliberately NOT touched**: unlike Teachers/Students/Classes (admin-only management, now gated by `requireSchoolAdmin()`), Attendance is legitimately used by both roles — a Teacher marks their own class's attendance, an Admin marks any class. The existing checks (`app/api/attendance/route.js`'s `getCurrentUser()` + `isClassInTeacherScope()`, `app/api/attendance/roster/route.js`'s same pattern, `.../[id]/lock/route.js`'s admin-only check) are the correct, already-real authorization model for this module and were left exactly as they were — this migration only changed where the data lives, not who's allowed to touch it.
- **`decorateAttendance()` reshapes the Prisma row back into the exact old flat shape** (`markedAt` converted back from a `DateTime` to the old ISO string) — **zero changes needed in any API route or component**, same payoff as every other migrated module here.
- **Verified end-to-end**: fetched the roster for a real class/section/date (Class 8 - A, ABC Public School) and confirmed real students returned; saved an attendance record via `POST /api/attendance` and confirmed it round-tripped through Postgres (re-fetching the roster showed `existingRecord` populated with the same id); locked/unlocked it via `PATCH /api/attendance/[id]/lock`; fetched a real student's monthly attendance stats (`GET /api/attendance/student/[id]?month=...`) and confirmed synthetic fallback status still fills in for days with no real saved record; `/dashboard/attendance/daily` and `/dashboard/attendance/reports` both confirmed rendering correctly before and after; test attendance row cleaned up afterward.

## `generateStudentFees()` Now Re-syncs Already-Generated PENDING Fees (Editing a Structure Actually Reaches Students)

Real bug report: admin generated Q1 fees, then edited the structure to add a missed "Admission Fee" item and clicked Generate again — the structure showed the new item, but already-generated student fees didn't change at all.

- **Root cause**: `generateStudentFees()` only ever created a `StudentFee` for a student who didn't have one yet for that session+term — a student who already had one (from the first generate) was unconditionally skipped, full stop, regardless of whether they'd actually paid.
- **Fix**: three-way split on the existing `StudentFee` (if any) for each eligible student — none → **create**; exists and still `PENDING`/`PARTIAL` → **update** (`items: { deleteMany: {}, create: ... }` + recompute `totalAmount`) to the structure's current items; exists and `PAID` → **left untouched**, since money already collected against the old items must never silently change underneath it. Return shape gained `updatedCount` alongside `generatedCount`/`skippedCount` (skipped now specifically means "already paid, protected"). `GenerateFeesModal.jsx`'s success message reports all three counts distinctly.
- **Verified on real data**: an already-generated PENDING fee (₹7,000, 4 items) correctly grew to ₹10,000 with the new item after re-generating; a fee manually marked PAID at ₹10,000 stayed at exactly ₹10,000 after the structure's amount was bumped further and Generate was run again (`skippedCount: 1`), while 24 other PENDING fees in the same run correctly picked up the new total (`updatedCount: 24`).

## Route-Level Protection Finally Added — `middleware.js` Now Guards `/dashboard/*`, `/super-admin/*`, `/parent/*`, Plus Guest-Only Redirects

Closed the gap documented in multiple places above ("Backend Migration: Auth API on Postgres + Prisma", "Auth APIs Converted to Server Actions"): a real `edumanage_session` JWT existed since those entries, but nothing checked it at the page level for `/dashboard/*`/`/super-admin/*` — anyone could open those URLs directly with no session at all. Surfaced while deploying to Vercel: `/super-admin/schools` and `/super-admin/admins` had no auth guard either, which is what prompted this.

- **`middleware.js` was already doing `/api/**` CORS** (unrelated, pre-existing) — extended in place rather than adding a second middleware file. Verifies the cookie via `lib/auth/jwt.js`'s `verifySessionToken` directly (pure `jose`, no `next/headers` dependency, so it's safe to call from the edge runtime middleware itself instead of needing `lib/auth/session.js`'s `getSession()`, which requires a request/page context).
- **Protected**: `/dashboard/*` requires role `SchoolAdmin`, `Teacher`, or `SuperAdmin` (the last because `app/api/schools/[id]/manage/route.js`'s "Manage This School" flow never upgrades the real session cookie, only `lib/currentUser.js`'s in-memory toggle — a Super Admin who's stepped into a school still carries a real `SuperAdmin` session and would otherwise be locked out of the very module they stepped in to manage). `/super-admin/*` requires role `SuperAdmin` only. `/parent/*` requires role `Parent` (this was already enforced in `app/parent/layout.jsx`; middleware now fails the request before that layout's DB reads even run, for an outright-unauthenticated hit). Anything unauthenticated/wrong-role redirects to `/login` (`/super-admin/*` redirects to `/` instead, since that's the actual Super Admin sign-in page).
- **Guest-only routes**: `/`, `/login`, `/forgot-password` — a visitor who already has a valid session of any role gets redirected straight to their own area (`SuperAdmin` → `/super-admin/schools`, `Parent` → `/parent`, `SchoolAdmin`/`Teacher` → `/dashboard`) instead of seeing a sign-in form again.
- **Deliberately left unguarded**: `/setup` (pre-account-creation onboarding wizard) and `/set-password` (token-in-URL flow for a teacher's first password set, not session-based) — neither fits the guest/protected split cleanly and neither was the reported gap.
- **Verified end-to-end** (local dev server, hand-signed JWTs via the same `signSessionToken`-equivalent pattern used elsewhere in this doc, real curl requests): no session → `/dashboard` redirects to `/login` (307), `/super-admin/schools` redirects to `/` (307), `/parent` redirects to `/login` (307), `/login` and `/` both still 200. `SchoolAdmin` session → `/dashboard` reachable, `/login` and `/` both redirect to `/dashboard`, `/super-admin/schools` still redirects to `/` (correctly blocked). `SuperAdmin` session → both `/dashboard` and `/super-admin/schools` reachable (200, no redirect) — confirms the "stepped into a school" exception. `/api/students` unaffected either way (its own existing `requireSchoolAdmin()` check still returns `401`, untouched by this change).
